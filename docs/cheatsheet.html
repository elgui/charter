Every day: the unit loop

One unit per deliverable. The agent runs steps 1 to 7; the teal lane is yours. Source: docs/daily-use.md § The loop.

Open a session

Read the banner:

charter 0.4.11, track prototype, opt-ins: none
  • charter next: active unit, road, next units, what waits on you. Writes nothing.
  • Hook not active: charter setup once.
  • On 0.4.2 or older you see no banner: charter config.

Pick or write the unit

start unit <id> or write a unit for … (skill charter-unit).

Ready when each AC names a probe that fails now ((guard) if it protects what works), perimeter: lists the paths, scope: is set on client, rail: where there are rails.

Start it

charter unit start <id>
charter probe <id> → exit 1 (ModuleNotFoundError …)

That failure is the baseline, the session's first ## Log line. A probe passing now proves nothing.

Work

  • Outside perimeter:? Add - path: why under ## Outside perimeter.
  • record the decision: charter/decisions/<slug>.md, cited in code as charter:<slug>.
  • Frozen file (800 lines; 400 for governance): move code out.
  • Unsold work: a change request.
  • Dated ## Log line when something lands.

Commit

On a branch. The hook runs charter check --staged:

charter check: 0 blocking, 0 warning(s) [staged, …]

Refused: each line ends with Override:; do that. Never --no-verify or a Bash workaround: CI runs the same checks.

Close it

finish the unit

  1. charter probe <id> → exit 0
  2. tick - [x] AC-n
  3. ## Evidence: SHA, path:line, the $ command lines
  4. status: done, closing log line
  5. charter unit stop

Final message cites the same, or the Stop hook blocks it once.

Report

where does this stand? (skill charter-progress)

charter ledger fold
charter synth --write

Writes charter/progress.md, or refuses if a line is unanchored. Never hand-edited. A client gets scope and accepted units.

OOnly you
Commit what is handed over (install, config, settings), one line after ! or in a terminal: CHARTER_OWNER=1 python3 <root>/.charter/bin/charter owner commit. charter handover prints it again.
Rule a proposal: charter rule <id> active|rejected, or rule <old> superseded --by <new>. Approve a change: charter approve <id> [--reject]. Each commits itself.
Let a frozen file grow: a kind: split unit, or a size_exceptions entry (budget, because:, expires:).
Re-plan: add or reorder rows in charter/rails.md; charter rail <id> done closes one.
Push, open, merge with a merge commit, which keeps evidence SHAs. Deploy.
Your queue: charter owner, each item with its command, a chain's wait included. Answer the agent's commitments (price, dates, data, releases).

A new project

Say install charter on <project>. The agent follows docs/install.md and stops with the files staged. $P is the project; counts are from a 0.4.11 rehearsal.

  1. 0Preconditions. A git repo with a commit; a clean tree; no other session in it; charter-pkg status $P → installed: none.
  2. 3Branch. git -C $P switch -c charter/install, never the main line.
  3. 4Dry run. charter-pkg install $P --track prototype --dry-run → dry run: 45 change(s). Watch for KEEP git hooks (step 6) and IGNORED by (ask the owner).
  4. 5Install. The same without --dry-run. Run again: already installed … nothing to do.
  5. 6Only after KEEP git hooks: add python3 -B .charter/bin/charter check --staged to the lefthook, pre-commit or husky hook.
  6. 7Staged by the installer, by name (44 files); a step 6 file you stage by name. Never git add -A.
  7. 8You commit. Set "owner" in charter/config.json to your git author name; charter config shows no problem:; run the handed-over git -C $P commit … -- <paths>. The agent's attempt gets 2 blocking (settings, config): expected.
  8. 9Verify. charter check --all → 0 blocking; charter-pkg status $P → 0 modified, missing, differing; a new session shows the banner; a fresh clone passes check --all --strict.
O You push and merge (merge commit). Each other clone: charter setup once. Client track: you write charter/scope.md from the signed devis, one item per sold deliverable, no prices.
Later, a new version: charter-pkg fleet --upgrade upgrades each project behind, commits it when only package files changed, hands over the rest. One by hand: docs/install.md § Upgrade. Rollback: git revert.

Migrating an existing project

Say put charter on <project>: CharterAdmin runs its Migrate workflow. Nothing touches the project before your go-ahead.

  1. 1Survey, read-only. charter-pkg survey $P --track prototype --out <dir outside>: survey.md, plan.md, an install rehearsed in a throwaway clone. --test-cmd exit 0: probes can run at commit.
  2. 2Settle what the facts settle. A lookup is not a decision; a proposal is not a scope.
  3. 3Your calls on a Slate, including the go-ahead for the real tree.
  4. 4Rehearse the whole plan in a kept clone (--keep-clone), the only place CHARTER_OWNER=1 is allowed.
  5. 5Execute in a worktree on charter/install: one step, one commit, one check; red stops it; owner-only steps wait staged.
  6. 6You push and merge. The agent reports each step with its check, and what is left.

The old work: a tasket listed in charter/legacy-taskets.txt closes with a warning only; units done before show as Done before charter in charter synth.

Running units in a chain

Say /charter-chain <unit> <your words>. This session starts it on chain/<id> and watches; fresh sessions work, each checking the last, handing over at 25% of context (cap 30%). Codex reviews each group; the next session answers each finding. Ends complete, halted (its reason is your question) or stopped. Keep out of the clone meanwhile. This machine's /supervise road: back.

O It waits on you: ! python3 .charter/bin/charter owner run runs the acts in your shell (--only N reruns one), then /resume-chain ok closes the lines whose acts passed; skip <note> closes none; a halt: /resume-chain <note>. Only you can resume it.

charter chain status names each group's cleared commit: merge up to one, never by squash. chain report is the PR comment.

Once a week

docs/daily-use.md § The owner's weekly look

  • charter next: Waiting on the owner lists proposals, finished rails, files staged for you. charter owner: that queue alone, with each command.
  • charter synth, no --write: adds gate activity.
  • charter log: 30 days of refusals and warnings. A warning that keeps catching real problems is evidence for a gate; one that fires on nothing is noise.
  • No new gates before two or three projects finish a full cycle (your ruling, 2026-09-24).
  • charter config, then opt in only when the project can bear it: probes.at_commit/in_ci when probes run offline and fast; probes.base_must_fail when they reliably fail first; review.required with an independent reviewer; rails.required when every open unit names a rail.

Words on this sheet

act: a step only the owner can take while a chain waits, written in owner.md with the owner lines it closes; charter owner run runs them. ▪ anchor: what a claim points to, so it can be checked: a path:line, a commit, a $ command run, a URL. ▪ change request: charter/changes/<id>.md: work outside the scope, until the owner approves it. ▪ decision: charter/decisions/<id>.md: a choice code depends on, cited as charter:<id>; its check:, if any, enforces it. ▪ evidence: what done needs under ## Evidence: a SHA that resolves, a $ command run → exit 0, a path:line beside them, every anchor resolving; never a path or URL alone, nor “it works”. ▪ frozen file: over its limit (800 lines; 400 for governance: rules, scope, decisions): it may shrink, not grow, unless the owner opens a split unit (kind: split) or a size_exceptions entry. ▪ gate: a check at each edit, commit and CI run. A hard gate refuses and names its Override, the way through; the others warn and log. ▪ group: in a chain, the units of one rail item. Codex reviews its commits; the commit where every finding is answered (its end, if none) is its cleared commit. ▪ handover: charter handover prints the owner's one line that commits what the agent staged. In a chain, a session hands over: its handoff, then charter chain next. ▪ ledger: charter/ledger.jsonl: tokens and estimated cost per session and unit, and your minutes. ▪ opt-in: a stricter setting the owner turns on in config.json (front, Once a week). ▪ owner: whom "owner" names in config.json. Owner-only: what only the owner changes (below); the agent's edit is refused, CI checks the author. ▪ probe: a command that proves one criterion: it fails before the work, passes after; passing before warns (refused with probes.base_must_fail). ▪ rails: charter/rails.md, the owner's plan: one rail item per row, with a status and an order. The road: the open items in order and their units, as charter next lists them. ▪ scope: charter/scope.md, the signed devis summed up, one item per sold deliverable. ▪ synthesis: charter/progress.md, written by charter synth, every line anchored. ▪ track: client under a signed devis or contract: scope.md required, and scope, perimeter note and anchored reports refuse. Else prototype: no scope, and the other two warn. Done, size and decisions refuse on both. ▪ unit, tasket: one deliverable, a markdown file in .taskets/ (left). ▪ wait, halt: a chain waits on acts, once the rest is done; it halts for your answer: a session's question, a review that cannot run, two sessions landing nothing, the session limit. Only your /resume-chain goes on. Defined where used: baseline, guard (front 2-3); chain (front); perimeter, owner line (left 3-4); commitment (below).

Personal layer: work the road unattended

This machine only, needs tele-claude; it merges each PR it verifies. The package's own way is the chain (front).

/supervise --road [--context-cap 25] [--max-units N]: the units in charter next order, one run each; verifies each PR, merges it via /reviewPR, closes the unit. Stops on a problem, the cap, an empty road.

/supervise --road --infinite [<project>]: stops only for you. Hands over at the cap, waits out limits, parks a blocked unit with what builds on it. Pushes its own .taskets/-only commits.

With --infinite, all optional; left out, the first two are asked once at the start
--week-target 70The week's usage it may reach, paced: a day's share at once, then even. 70 a working week, 90 a week off; none: the 95% cap only.
--stop-at-rail <id>End before this rail; offered: after-active, before-parked, the whole road.
--max-units 2A first trial on a new project.
--gate "<cmd>"One command judges every merge; else worked out per unit (decisions' check:, its tests, what imports the change). Files red on main at the start cannot fail it.

Start sweep, what needs you: grant a kind of change, review (PR parked), keep a gate: human, last, hold. Unit keys: on_block: park|stop, road_grant, road_review.

Running: Road.py tally report --file <state>; say stop the road; --resume <state>. A cron keeper wakes it.

Always: no launch past 85% of the 5-hour window, 95% of the week, or 00:00–06:00 Paris.
