Every day: the unit loop

One unit per deliverable. The agent runs steps 1 to 7; the teal lane is yours. Source: docs/daily-use.md § The loop.

Open a session

Read the banner:

charter 0.4.4, track prototype, opt-ins: none
  • charter next: active unit, road, next units, what waits on you. Writes nothing.
  • Hook not active: charter setup once.
  • On 0.4.2 or older you see no banner: charter config.

Pick or write the unit

start unit <id> or write a unit for … (skill charter-unit).

Ready when each AC names a probe that fails now ((guard) if it protects what works), perimeter: lists the paths, scope: is set on client, rail: where there are rails.

Start it

charter unit start <id>
charter probe <id> → exit 1 (ModuleNotFoundError …)

That failure is the baseline, the session's first ## Log line. A probe passing now proves nothing.

Work

  • Outside perimeter:? Add - path: why under ## Outside perimeter.
  • record the decision: charter/decisions/<slug>.md, cited in code as charter:<slug>.
  • Frozen file (800 lines; 400 for governance): move code out.
  • Unsold work: a change request.
  • Dated ## Log line when something lands.

Commit

On a branch. The hook runs charter check --staged:

charter check: 0 blocking, 0 warning(s) [staged, …]

Refused: each line ends with Override:; do that. Never --no-verify or a Bash workaround: CI runs the same checks.

Close it

finish the unit

  1. charter probe <id> → exit 0
  2. tick - [x] AC-n
  3. ## Evidence: SHA, path:line, the $ command lines
  4. status: done, closing log line
  5. charter unit stop

Final message cites the same, or the Stop hook blocks it once.

Report

where does this stand? (skill charter-progress)

charter ledger fold
charter synth --write

Writes charter/progress.md, or refuses if a line is unanchored. Never hand-edited. A client gets scope and accepted units.

OOnly you
Commit what was staged for you (install, upgrade, config, rails): git commit in your own terminal, or CHARTER_OWNER=1 git commit after ! in Claude Code.
Approve a change request: status: approved, approved_by:, approved_on:. Retire a decision: status: superseded, superseded_by:.
Let a frozen file grow: a kind: split unit, or a size_exceptions entry (budget, because:, expires:).
Re-plan: add or reorder rows in charter/rails.md.
Push, open, merge with a merge commit, which keeps evidence SHAs. Deploy.
Decide proposed decisions; answer the agent's commitments (price, dates, data, releases).

A new project

Say install charter on <project>. The agent follows docs/install.md and stops with the files staged. $P is the project; counts are from the 0.4.4 rehearsal.

  1. 0Preconditions. A git repo with a commit; a clean tree; no other session in it; charter-pkg status $P → installed: none.
  2. 3Branch. git -C $P switch -c charter/install, never the main line.
  3. 4Dry run. charter-pkg install $P --track prototype --dry-run → dry run: 35 change(s). Watch for KEEP git hooks (step 6) and IGNORED by (ask the owner).
  4. 5Install. The same without --dry-run. Run again: already installed … nothing to do.
  5. 6Only after KEEP git hooks: add python3 -B .charter/bin/charter check --staged to the lefthook, pre-commit or husky hook.
  6. 7Stage by name (34 files), never git add -A.
  7. 8You commit. Set "owner" in charter/config.json to your git author name; charter config shows no problem:; git commit -m "charter 0.4.4". The agent's own attempt gets 16 blocking: expected.
  8. 9Verify. charter check --all → 0 blocking; charter-pkg status $P → 0 modified, missing, differing; a new session shows the banner; a fresh clone passes check --all --strict.
O You push and merge (merge commit). Each other clone: charter setup once. Client track: you write charter/scope.md from the signed devis, one item per sold deliverable, no prices.

Migrating an existing project

Say put charter on <project>: CharterAdmin runs its Migrate workflow. Nothing touches the project before your go-ahead.

  1. 1Survey, read-only. charter-pkg survey $P --track prototype --out <dir outside> writes survey.md and plan.md and rehearses the install in a throwaway clone. --test-cmd "<tests>" exit 0: probes can run at commit.
  2. 2Settle what the facts settle. A lookup is not a decision; a proposal is not a scope.
  3. 3Your calls on a Slate, including the go-ahead for the real tree.
  4. 4Rehearse the whole plan in a kept clone (--keep-clone), the only place CHARTER_OWNER=1 is allowed.
  5. 5Execute, after the go-ahead, in a worktree on charter/install: one step, one commit, one check; a red check stops it. Owner-only steps stop staged for O.
  6. 6You push and merge. The agent reports each step with its check, and what is left.

What happens to the old work

  • Taskets with neither ## Acceptance nor scope: are listed in charter/legacy-taskets.txt; closing one only warns.
  • Units done before the install show under Done before charter in charter synth, not as failures.
  • Triage by batch: each open tasket gets scope:, perimeter: and probes, or is parked with a reason; its id leaves the legacy list.
  • CLAUDE.md rulings become decisions; progress files are archived, since charter synth replaces them; BMAD plans stay as inputs, stories stop.

A unit, .taskets/<id>.md

--- id: 20260925-greet title: A greeting function status: next 1 scope: S1 2 rail: r1-greet perimeter: [app/**] 3 kind: work --- ## Acceptance 4 - [ ] AC-1: greet() returns hello — probe: `python3 -c "…"` - [ ] AC-2: (guard) old API intact — probe: `pytest tests/api -q` ## Evidence 5 - a76f695 adds greet (app/greet.py:1-2) - `$ python3 -c "…"` → exit 0 ## Log 6 - 2026-09-25 09:00 started; baseline AC-1 → exit 1 ## Outside perimeter
  1. 1now next later blocked done; closed without evidence, honestly: parked, skipped. Comments go on their own line, never after a value.
  2. 2scope: an in-scope item or an approved change (client track). rail: an open item of charter/rails.md.
  3. 3Paths it may touch. Outside them, a note under ## Outside perimeter: refused at commit on client, warns on prototype.
  4. 4One binary probe per line, written before the code, failing before the work. Once the unit leaves next/later, changing a line needs a dated log line.
  5. 5A commit, a path:line, the $ command lines charter probe printed. With review.required: - review: <who, model> — <verdict> — <anchor>.
  6. 6Append-only and dated. The next session resumes from here, not from the transcript.

Evidence the done gate accepts

  • counts a commit SHA that resolves
  • counts $ command → exit 0, as run
  • counts path:line of the change, beside a commit or run
  • counts every - [x] ticked after its probe passed
  • refused a path or a URL alone
  • refused “it works”, “tests pass”
  • refused an anchor that does not resolve
  • refused one box left [ ]

A probe that passes before the work warns (refused with probes.base_must_fail). The gate sees that evidence resolves, not that it proves the claim: that is the reviewer's job, and yours.
