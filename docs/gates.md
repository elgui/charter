# Hooks and gates reference

Every gate lives in `package/.charter/checks.py` and is called from three places: the Claude Code hooks in `package/.charter/hooks/`, the git hook `package/.charter/githooks/pre-commit` (through `charter check --staged`), and CI (`package/.github/workflows/charter.yml`, through `charter check --all --ci` and `charter anchors`). Every finding is appended to `log.jsonl` in the git common directory (`.git/charter/` in a normal clone, shared by every worktree, never committed) with its gate, level, path and the event that raised it; `charter log` summarises it.

Hook contract facts this design rests on (https://code.claude.com/docs/en/hooks, fetched 2026-09-11): `PreToolUse` denies through `hookSpecificOutput.permissionDecision: "deny"` and the reason reaches Claude; `PostToolUse` cannot block, but exit 2 puts stderr in front of Claude; `Stop` blocks with `decision: "block"`, and `hookSpecificOutput.additionalContext` on `Stop` is "non-error feedback" that continues the conversation; both receive `stop_hook_active` and Claude Code ends the turn after eight consecutive continuations; a `systemMessage` is shown to the user, not to Claude; a hook process inherits Claude Code's environment; `-p` runs treat the folder as trusted so committed project hooks run; `${CLAUDE_PROJECT_DIR}` stays at the session's start directory when Claude enters a worktree while `cwd` in the hook input follows it; hook stdout is capped at 10,000 characters. A saved change to a settings file's `env` block is applied to the running session (https://code.claude.com/docs/en/settings-reference, section `env`, "When Claude Code applies `env` values"). Claude Code sets `CLAUDECODE=1` in the subprocesses it spawns, its Bash tool included, and IDE extensions set it in their integrated terminals (https://code.claude.com/docs/en/env-vars).

## Owner-only changes (R3, R6, R7, rails)

The files and fields that decide what the gates enforce are the owner's. `owner_only_changes` in `package/.charter/checks.py` lists them:

| What | Why |
|---|---|
| `charter/scope.md`, `charter/rails.md`, `charter/config.json` (limits, `rails`, `exempt_from_size`, `size_exceptions`, `governance_files` among its keys), `.charter/**`, `.claude/settings.json`, `.claude/settings.local.json`, `.github/workflows/charter.yml` | They define the gates and their wiring |
| An id added to `charter/legacy-taskets.txt` | It exempts that tasket from the done gate; removing an id is free (`owner_only_changes` in `package/.charter/checks.py`) |
| A change request's `status:` (other than a new `proposed` one), `approved_by:`, `approved_on:`; the `paths:` of an approved one | Only the owner approves (R7) (`owner_only_changes` in `package/.charter/checks.py`) |
| An existing decision's `status:` and `superseded_by:`; the `check:` and `binds:` of an active one | Retiring or weakening a decision turns its gate off; an agent proposes a successor instead (`owner_only_changes` in `package/.charter/checks.py`) |
| Opening a `kind: split` unit, adding a path to its perimeter, or reopening a closed one | It unfreezes files for the size gate (R3); narrowing or closing one is free (`owner_only_changes` in `package/.charter/checks.py`) |
| Any edit that introduces `CHARTER_OWNER` (in session only) to a file inside the project, or to a Claude Code settings file anywhere: `settings.json`, `settings.local.json`, `managed-settings.json` or a `managed-settings.d/*.json`, by name and through a link (`reaches_the_session`) | A settings `env` block would switch these checks off mid-session ([settings](https://code.claude.com/docs/en/settings), [managed settings](https://code.claude.com/docs/en/managed-settings)); any other file outside the project, such as a scratchpad, reaches nothing and is allowed |
| `charter/ledger.jsonl` (in session only) | Written by `charter ledger`, never by hand; committing what the CLI wrote is allowed (`owner_only_changes` in `package/.charter/checks.py`) |

Where each layer enforces it:

- **PreToolUse** denies the Edit or Write unless Claude Code was started with `CHARTER_OWNER=1` (`lib.owner_session`). The reason names the override: the owner edits the file, or proposes (`package/.charter/hooks/pre_tool_gate.py`).
- **Pre-commit** refuses the change when the commit runs inside Claude Code (`CLAUDECODE=1`) without `CHARTER_OWNER=1`; outside Claude Code it warns, because the committer cannot be told apart from the owner. From an IDE terminal where the Claude extension sets `CLAUDECODE`, the owner commits with `CHARTER_OWNER=1` (`check_owner_only_staged` in `package/.charter/checks.py`; `in_claude_code` in `package/.charter/lib.py`).
- **CI** refuses a commit in the change set whose author name or email is not `owner` in `charter/config.json` **as the base revision has it** (so a change set cannot name its own author the owner; only the install, whose base has no config, reads the config under review) when it makes an owner-only change (`check_owner_commits`); with no `owner` set it warns. A merge commit answers for content no parent had and for any side's change since the merge base that it drops; it is not blamed for an owner change it carries over from the other side. CI also refuses any file under `.charter/` whose SHA-256 differs from `.charter/manifest.json` and warns on the other owned files, the workflow included, whose block comes from the author check (`check_manifest`) (`package/.charter/checks.py`).

What this cannot do, stated in `docs/review/2026-09-11-weakness-evaluation.md`: a Bash command is not an Edit or a Write, the agent commits under the owner's git identity on the owner's machine, and a pull request can edit the workflow that checks it. The locks are outside the repository: GitHub branch protection with required review, and code owners for the files above (https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners).

## The gates

### Scope (R6): out-of-scope path without an approved change request

- Checks: an edited or staged path matches the `paths:` of an item under `## Out of scope` in `charter/scope.md` and no change request with `status: approved`, `approved_by:` and `approved_on:` lists a glob covering it. Only on `track: client`. Headings are matched ignoring case, hyphens and underscores (`## Out-of-Scope` counts); an item heading without an id (`### Invoicing`) is still gated under its heading (`check_scope` in `package/.charter/checks.py`; `parse_scope` in `package/.charter/lib.py`).
- Blocks: `PreToolUse` deny; pre-commit; CI on the paths changed since the merge base of `--base` (PR base SHA or the push's previous SHA). Files already out of scope before the change set are a warning ("legacy"). When the base is unusable (an all-zero SHA when a branch is created, a SHA a force-push removed), every tracked path counts as changed and a warning says so (`_check` in `package/.charter/bin/charter`).
- Override: write the change request from `charter/templates/change.md`; the owner sets `status: approved`, `approved_by:`, `approved_on:`. `charter check` refuses `approved` without the two fields (R7). Recorded in `charter/changes/<slug>.md`; the approval is a commit by the owner (`check_changes` in `package/.charter/checks.py`; template `package/charter/templates/change.md`).
- Also: a unit whose `scope:` names an unknown id is refused; a unit with no `scope:` is a warning; a unit whose `perimeter:` reaches an out-of-scope path, or is not covered by the paths of the item it cites, is a warning; `charter check --scope` reports what makes the scope file fail open (no in-scope item, an out-of-scope item without `paths:`, an item without an id, a `###` item under an unknown `##` section) (`check_unit_scope` and `check_scope_file` in `package/.charter/checks.py`).

### Rails (R6 without a devis): open work the road does not name

- Checks: when `charter/rails.md` exists (the path is fixed, so the staged view and the owner-only list both cover it), every open unit names one of its items, with `rail: <id>` or a `roadmap:` link whose `#anchor` is the id (`rails.keys`, by default `rail` and `roadmap`). The first key (`rail:` by default) always decides. A `roadmap:` anchor counts only when it names a known rail, because it links a document section and a section that is not a rail declares nothing. Otherwise the unit is on every rail whose optional `groups` column (comma-separated globs) matches its `group:`, which links a whole plan group without editing each unit. At commit only the units in the change set are judged; `--all` reports the backlog. The file's first table with the columns `id`, `title`, `status`, `order` holds the items; statuses are `todo`, `next`, `in-progress`, `done`, `parked`, `dropped`. An open unit is one whose status is neither in `done_statuses` nor terminal. Such a unit that names no rail, or only ids the file does not list, is a warning. One whose rails are all closed (`done`, `parked`, `dropped`) is also a warning. A duplicate id, an unknown status or a non-integer order in the file is warned (`parse`, `rails_of` and `check` in `package/.charter/rails.py`; `tests/test_rails.py`).
- Blocks: only with `"rails": {"required": true}`, and only for a unit in the change set: pre-commit and CI. A unit written before the rails existed never blocks an unrelated commit (`check` in `package/.charter/rails.py`).
- Override: name an open item. To start work the road does not name, the owner adds an item to `charter/rails.md` first. That commit is the recorded re-plan, and the file is owner-only (`OVERRIDE` in `package/.charter/rails.py`; `package/.claude/rules/charter.md:32`).
- Synthesis: `charter synth` prints the rails in order, each with the units that cite it and their states, then the open units that are off the rails. For a project without a devis, this replaces a hand-kept tracker. A tasket file git ignores is local scratch, not a unit: the gates and the synthesis skip it, because a synthesis citing it fails its anchors in CI, where it does not exist (`taskets` in `package/.charter/lib.py`; `synth_lines` in `package/.charter/rails.py`).
- On the client track the scope gate does the same job against `charter/scope.md`. The two can run together (`package/.charter/rails.py`, `check_scope` in `package/.charter/checks.py`).

### Size (R3): frozen file

- Checks: after the edit, in the staged version, or at HEAD against the change set's base, the file exceeds `limits.file_lines` (800 by default) and grew. Governance files use `limits.governance_lines` (400) **and** `limits.governance_bytes` (32768): one long line counts as one line, so a governance file past either is frozen. The governance set is `governance_files` in `charter/config.json`, globs, by default `CLAUDE.md`, `AGENTS.md`, `charter/scope.md` and `.claude/rules/*.md`; `charter/decisions/*` and `charter/changes/*` are always in it. Globs in `exempt_from_size` and the package's own `.charter/` are skipped, and so is binary content (a NUL byte in the first 8,000 bytes, the test git itself uses), for which a line count means nothing. At 80% of a limit a warning says to plan a split.
- Named exceptions: `size_exceptions` in `charter/config.json` lists `{path, lines and/or bytes, because, expires}`. A live entry replaces the limit it names for that one path, so open work can grow a file the owner has budgeted without a split unit. An entry without `because:` or a dated `expires:`, or without a positive budget, is ignored and warned by `charter check`. Expiry is exclusive, as for decisions: on its `expires:` date the entry has stopped, `charter check` warns, and the block message names the date. The file is owner-only, so an agent cannot add or widen an entry (`size_exceptions` in `package/.charter/checks.py`; `tests/test_size_exceptions.py`).
- Blocks: `PreToolUse` deny; pre-commit; CI for a file that grew past the limit in the change set. `--strict` reports every file over the limit, grown or not (`check_size` in `package/.charter/checks.py`).
- Override: move code out of the file (shrinking is always allowed), a `size_exceptions` entry the owner writes, or an open unit with `kind: split` that names the file in its `perimeter:` as a literal path; a glob does not count. The owner opens the split unit. While it is open the file may grow (warning only), so the split can be done in steps. Recorded in that unit's `## Log` and `## Evidence` (`check_size` and `split_unit_for` in `package/.charter/checks.py`).

### Done needs evidence (R9)

- Checks: a tasket whose `status` is in `done_statuses` must have a `## Acceptance` checklist (`## Done When`, the Tasket skill's heading, counts too) with every box checked and a `## Evidence` section that names a commit `git cat-file -e` finds or a `$ command` run; a path or a URL alone is refused. Anchors that do not resolve are refused. A unit that has left `next` or `later` cannot remove or rewrite an acceptance line without a new `## Log` line in the same change.
- Blocks: `PreToolUse` deny on the tasket edit; pre-commit and CI for a tasket whose status changes to done in the change set (with `--strict`, every done tasket) (`check_unit_done` in `package/.charter/checks.py`).
- Probes: with `--probe`, or `probes.at_commit` / `probes.in_ci` in `charter/config.json`, the probes of each unit that closes in the change set are run from the repository root with `probes.timeout_s`; a non-zero exit blocks. At commit they run only when the working tree matches the index. `charter probe <id>` runs them on demand and prints the `$ command` lines to paste as evidence.
- Probes before the work: when a closing unit's probes pass, each is run again in a detached worktree at the parent of the commit that added the unit's file (at `HEAD` when the file is not committed yet). One that passes there does not test the change: a warning, a block with `probes.base_must_fail`. A criterion whose line contains `(guard)` is skipped, because it protects existing behaviour. The worktree has only tracked files, so a probe that needs untracked dependencies (`node_modules`, a virtualenv) fails there and is not reported; that errs towards letting a weak probe through. A unit added in the repository's first commit has no base and is not checked. Tests: `tests/test_probe_at_base.py`.
- Independent review (opt-in): with `review.required` in `charter/config.json`, done also needs a `- review: <reviewer and model> — <verdict> — <anchor>` line under `## Evidence` whose anchor resolves (a PR comment URL, a commit, a `$ command` run). It is meant for a verdict from a different model family than the one that wrote the code, such as the codex review. It is checked wherever the done gate runs (PreToolUse, pre-commit, CI). The gate checks that the line exists and points somewhere; it cannot check that the review happened, or which model gave it. Tests: `tests/test_review_required.py`.
- Legacy: a tasket listed in `charter/legacy-taskets.txt` (written by the installer from the taskets it found) and without `## Acceptance` closes with a warning, even when it has `## Done When` (`check_unit_done` in `package/.charter/checks.py`).
- Override: none by flag. Keep the status open, or add the evidence. A tasket that must be closed without evidence is `parked` or `skipped`, both terminal for the engines and both honest (`TERMINAL_STATUSES` in `package/.charter/lib.py`).

### Decisions (R1)

- Checks: every `charter:<id>` marker in an edited or staged file names an existing decision; a decision with `status: superseded` or `retired` cannot be cited (the message names `superseded_by`). A file matching an active decision's `binds:` globs without its marker is a warning. Every active decision's `check:` command is run; a non-zero exit is "contradicted". Two files holding one decision or change id are refused. An open unit whose `decisions:` names a missing or retired decision is a warning (`check_decisions_text`, `duplicate_ids`, `run_decision_checks` and `check_unit_decisions` in `package/.charter/checks.py`).
- Blocks: `PreToolUse` deny for a retired citation or a taken id; `PostToolUse` exit 2 (stderr to Claude) when a bound file's check fails after the edit; pre-commit and CI for both. At commit only the decisions whose `binds:` match a staged path run their `check:`; one with no `binds:` runs in CI and in `charter check --all`, not at commit (`tests/test_review_20260923.py`). At commit the checks run in the working tree, so the commit is refused when the working tree differs from the index.
- Override: supersede the decision with a new record that sets `supersedes:`; the owner sets the old one to `superseded` with `superseded_by:`. The new record carries its own `## Because`. Recorded in `charter/decisions/` (template `package/charter/templates/decision.md`; `package/.claude/skills/charter-decision/SKILL.md`).

### Perimeter (R4)

- Checks: the active unit (`CHARTER_UNIT` from the environment, else the one `charter unit start` recorded in this worktree's git directory) declares `perimeter:` globs; an edited or staged path outside them, outside `.taskets/`, `charter/` and `.charter/`, and not named under the unit's `## Outside perimeter` section. A file that git ignores and does not track, such as a tool's local journal, is never the unit's work and is not checked (0.4.4, `lib.ignored`) (`check_perimeter` in `package/.charter/checks.py`).
- Blocks: `PostToolUse` warning in session; pre-commit block on the client track, warning on the prototype track; CI does not know the active unit and does not check this (`check_perimeter` in `package/.charter/checks.py`).
- Override: the note itself (`- path: why`), or widening `perimeter:`. No active unit is a warning ("edits are not attributed"), never a block (`check_perimeter` in `package/.charter/checks.py`).

### Memory (R8)

- Checks: an active decision without `## Because` or without `expires:`; a dated `expires:` on or before today, because expiry is exclusive and a decision stops applying at the start of that date; a dated `expires:` that is not later than the decision's `date:`; a `kind: lesson` without `owner:`. The boundary is the one tcv2's HARNESS.md uses for `expires_on` (https://github.com/elgui/tcv2/blob/936cb5618bdb98453b4a73e167670bccc74a27a5/services/harness_evidence.py).
- Warning only, in `charter check --memory` and CI output (`check_memory` in `package/.charter/checks.py`; `package/.github/workflows/charter.yml:18`).

### Stop gate (R9/R10 in the session)

- Judges only a turn that attempted an Edit or Write or moved HEAD; an explanation is not a completion claim (`package/.charter/hooks/stop_gate.py`).
- Checks: `last_assistant_message` contains a completion claim (done, complete, implemented, fixed, shipped, tests pass, a check mark) and no commit, `path:line` or `$ command` run, and does not admit "not done" or "unverified"; or the active unit is `done` and fails the done gate.
- Blocks once. The second Stop in the same turn passes through and logs `done/passed`. Reason text names what to cite. When a commit landed during the turn and the active unit's `## Log` did not move, `additionalContext` asks Claude to append the line; this costs one short continuation (`package/.charter/hooks/stop_gate.py`).

### Anchors (R10)

- Command: `charter anchors <file>...`, exit 1 on any unanchored claim line or unresolved anchor. Definitions in `docs/method.md` § Accepted results. Exempt sections: `<!-- charter: opinion -->` ... `<!-- charter: /opinion -->`. Admitted claims, by evidence class (`docs/method.md` § Evidence classes): reported `(reported in ...)`, `(operator report ...)`, `(claimed by ...)`, `(outside this repository ...)`, `(in the scratchpad ...)`, `(in the clone ...)`, `(on the test bed ...)`; inference `(inference ...)`, `(unverified)`, `(not verified)`, `(estimate ...)`, `(to be confirmed)`.
- `charter anchors --pr <file>` is the pull-request mode: `#123` and `owner/repo#123` count as anchors, an empty description is reported, and the result is a warning (exit 0). On the prototype track every anchors result is a warning.
- Runs in CI on `charter/progress.md`, `docs/progress*.md`, `docs/report*.md` (hard), and on the PR body in `--pr` mode, re-run when the body is edited. Not on decisions or the scope, whose statements are normative.
- `charter synth` runs it on its own output and refuses to write on failure. The written synthesis leaves out gate activity, which lives on one machine.

## Git hook

`package/.charter/githooks/pre-commit` runs `python3 -B .charter/bin/charter check --staged`. It reads `charter/` and `.taskets/` from the index (`lib.index_view`), so the commit is judged, not the working tree. Activated by `git config core.hooksPath .charter/githooks`, which is repository config and is not cloned: `python3 .charter/bin/charter setup` sets it in a clone, the installer sets it on every run, and the SessionStart banner says when it is missing. A project that already runs git hooks (lefthook, pre-commit, husky, scripts in `.git/hooks`) keeps them: the installer and `setup` then leave `core.hooksPath` alone unless `--replace-hooks`, and the gate runs as `python3 -B .charter/bin/charter check --staged` from the existing framework (`package/.charter/githooks/README.md`). A relative `core.hooksPath` resolves inside linked worktrees, verified in the trial (G7). `git commit --no-verify` skips it; CI runs the same checks.

The gate fails open on its own errors. `charter check` and `charter anchors` catch any unexpected exception: they print one line to stderr, log `error/error` (`charter log`), and exit 0, so the commit goes through ungated. A `charter/config.json` the gates cannot read is not such an error: since 0.4.3 it is refused (§ Config). Binary files are read without decoding errors and skipped by the size and decision checks.

## CI

`package/.github/workflows/charter.yml`: on pull requests (opened, edited, synchronize, reopened) and pushes to `main` and `staging`. It fetches `refs/pull/*/head` so an evidence commit a squash or rebase merge removed from the branch still resolves (GitHub documents fetching `pull/ID/head` and keeping a closed pull request's head branch restorable: https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/checking-out-pull-requests-locally, https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-branches-in-your-repository/deleting-and-restoring-branches-in-a-pull-request). Then `charter check --all --ci --base <sha>` where the base is the PR base SHA or the push's previous SHA; `charter anchors` on syntheses and reports; `charter anchors --pr` on the PR body. Probes run only when `probes.in_ci` is set, because the runner has Python 3 and nothing else unless the project installs its test dependencies in the workflow.

A gate that crashes in CI fails open as it does at commit: the step passes, so a crash never blocks a merge. When `GITHUB_ACTIONS` is `true` it also prints a `::warning` workflow command, which puts the error on the run's summary (https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands, "Setting a warning message"; https://docs.github.com/en/actions/reference/workflows-and-actions/variables, `GITHUB_ACTIONS`). The runner's gate log is gone when the job ends, so that annotation is the only trace.

## What a gate cannot see

- A `PreToolUse` hook does not run for an Edit whose `old_string` is absent from the file: Claude Code rejects that Edit first (trial T1c). It does not run for files added with `@` in a prompt, nor for files changed by a Bash command; the git hook and CI see those.
- The perimeter gate depends on the session declaring its unit. Nothing forces `charter unit start`; the log shows unattributed edits and the SessionStart banner says so.
- The done gate checks that a commit is named or a run is recorded, and with probes enabled that the probes pass and did not already pass before the unit. It does not check that they test the criterion: a probe that fails before for an unrelated reason, or a criterion marked `(guard)` without cause, passes. The reviewer agent and the owner check the truth.
- The scope gate matches paths. Work that is out of scope but lands in an in-scope path is invisible to it; the unit's `scope:` and the owner's review carry that.
- A permission denial (`--permission-prompts none`) and a gate denial read alike to the agent. The log distinguishes them.
- A `check:` is a shell command read from a markdown file and run at every commit and in CI. That is the feature; the SessionStart banner lists every one.
- Most of R7's operational commitments are actions, not files: a deployment, a change to production data or schema, a purchase, a public release, another person's work, a merge into main. No gate sees them; the rules file carries them. Widening a permission is gated where it is a file, since `.claude/settings.json` and `.claude/settings.local.json` are owner-only.

## Config

`charter/config.json` is read by `load_config` and `config_from` in `package/.charter/lib.py`, against `CONFIG_SCHEMA` there: the keys each section may hold and the type of each value. Before 0.4.3 any key was merged, so `{"rails": {"requird": true}}` left `rails.required` off and a track of `"prototpe"` switched the scope gate off (outside review, 2026-09-24; `tests/test_config_0_4_3.py`). Now:

- An unknown key, at the top or in a section, is not applied. The message suggests the nearest known key: ``unknown key `rails.requird` (did you mean `required`?); ignored``.
- A value of the wrong type keeps its default. JSON `true` is not accepted as a number.
- A track other than `client` or `prototype` is read as `client`, the stricter track.
- A file that is not JSON, or not a JSON object, leaves every setting at its default, track `client`.

Each of these is a `charter/config block [charter/config.json]` finding in `charter check`, so the commit that introduces it is refused at the git hook and in CI, with the override "the owner corrects charter/config.json". The config is judged as staged, like the rest of `charter/`. The SessionStart banner prints each problem with "Commits and CI are refused until the owner corrects it"; the session hooks keep running on the values that were applied. `python3 .charter/bin/charter config` prints what the gates read, `track <track>, opt-ins: <list or none>`, then one `problem:` line per problem, and exits 1 when there is one.

The opt-ins are `rails.required`, `probes.at_commit`, `probes.in_ci`, `probes.base_must_fail` and `review.required` (`OPT_INS` in `package/.charter/lib.py`). The ones that are on appear in the banner and at the end of every `charter check` summary line, `[staged, track client, opt-ins: review.required]`, so a CI log shows what it enforced.
