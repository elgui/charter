# Hooks and gates reference

Every gate lives in `package/.charter/checks.py` and is called from three places: the Claude Code hooks in `package/.charter/hooks/`, the git hook `package/.charter/githooks/pre-commit` (through `charter check --staged`), and CI (`package/.github/workflows/charter.yml`, through `charter check --all --ci` and `charter anchors`). Every finding is appended to `log.jsonl` in the git common directory (`.git/charter/` in a normal clone, shared by every worktree, never committed) with its gate, level, path and the event that raised it; `charter log` summarises it.

Hook contract facts this design rests on (https://code.claude.com/docs/en/hooks, fetched 2026-09-11): `PreToolUse` denies through `hookSpecificOutput.permissionDecision: "deny"` and the reason reaches Claude; `PostToolUse` cannot block, but exit 2 puts stderr in front of Claude; `Stop` blocks with `decision: "block"`, and `hookSpecificOutput.additionalContext` on `Stop` is "non-error feedback" that continues the conversation; both receive `stop_hook_active` and Claude Code ends the turn after eight consecutive continuations; a `systemMessage` is shown to the user, not to Claude; a hook process inherits Claude Code's environment; `-p` runs treat the folder as trusted so committed project hooks run; `${CLAUDE_PROJECT_DIR}` stays at the session's start directory when Claude enters a worktree while `cwd` in the hook input follows it; hook stdout is capped at 10,000 characters. A saved change to a settings file's `env` block is applied to the running session (https://code.claude.com/docs/en/settings-reference, section `env`, "When Claude Code applies `env` values"). Claude Code sets `CLAUDECODE=1` in the subprocesses it spawns, its Bash tool included, and IDE extensions set it in their integrated terminals (https://code.claude.com/docs/en/env-vars).

## Owner-only changes (R3, R6, R7, rails)

The files and fields that decide what the gates enforce are the owner's. `owner_only_changes` in `package/.charter/checks.py` lists them:

| What | Why |
|---|---|
| `charter/scope.md`, `charter/rails.md`, `charter/config.json` (limits, `rails`, `exempt_from_size`, `size_exceptions`, `governance_files` among its keys), `.charter/**`, `.claude/settings.json`, `.claude/settings.local.json`, `.github/workflows/charter.yml` | They define the gates and their wiring. At commit and in CI, a package file whose content hashes to what `.charter/manifest.json` records at the same revision, and a manifest whose every listed file matches, is an upgrade, not an owner-only change (`release_change` in `package/.charter/checks.py`, from 0.4.6). A hand edit of the engine does not match. An edit that also rewrites the manifest does, and is the case below, "What this cannot do": the hook that would refuse it runs from the tree it edits |
| An id added to `charter/legacy-taskets.txt` | It exempts that tasket from the done gate; removing an id is free (`owner_only_changes` in `package/.charter/checks.py`) |
| A change request's `status:` (other than a new `proposed` one), `approved_by:`, `approved_on:`; the `paths:` of an approved one | Only the owner approves (R7) (`owner_only_changes` in `package/.charter/checks.py`) |
| An existing decision's `status:` and `superseded_by:`; the `check:` and `binds:` of an active one | Retiring or weakening a decision turns its gate off; an agent proposes a successor instead (`owner_only_changes` in `package/.charter/checks.py`) |
| Closing an acceptance line marked `— owner: do`, `check` or `decide`: ticking it, removing its mark, removing it, and adding one already ticked | The owner closes it: a session that closed it would pass for the owner's act, as an agent did in the wait trial (`docs/trials/2026-10-04-owner-gate.md`). Marking a line and reopening one are free. The line is known by its AC id, else by its text (`owner_line_changes` in `package/.charter/checks.py`; `tests/test_owner_gate.py`) |
| Opening a `kind: split` unit, adding a path to its perimeter, or reopening a closed one | It unfreezes files for the size gate (R3); narrowing or closing one is free (`owner_only_changes` in `package/.charter/checks.py`) |
| Any edit that introduces `CHARTER_OWNER` (in session only) to a file inside the project, or to a Claude Code settings file anywhere: `settings.json`, `settings.local.json`, `managed-settings.json` or a `managed-settings.d/*.json`, by name and through a link (`reaches_the_session`) | A settings `env` block would switch these checks off mid-session ([settings](https://code.claude.com/docs/en/settings), [managed settings](https://code.claude.com/docs/en/managed-settings)); any other file outside the project, such as a scratchpad, reaches nothing and is allowed |
| `charter/ledger.jsonl` (in session only) | Written by `charter ledger`, never by hand; committing what the CLI wrote is allowed (`owner_only_changes` in `package/.charter/checks.py`) |

Where each layer enforces it:

- **PreToolUse** denies the Edit or Write unless Claude Code was started with `CHARTER_OWNER=1` (`lib.owner_session`). The reason names the override: the owner edits the file, or proposes (`package/.charter/hooks/pre_tool_gate.py`).
- **Pre-commit** refuses the change when the commit runs inside Claude Code (`CLAUDECODE=1`) without `CHARTER_OWNER=1`; outside Claude Code it warns, because the committer cannot be told apart from the owner. From an IDE terminal where the Claude extension sets `CLAUDECODE`, the owner commits with `CHARTER_OWNER=1` (`check_owner_only_staged` in `package/.charter/checks.py`; `in_claude_code` in `package/.charter/lib.py`).
- **CI** refuses a commit in the change set whose author name or email is not `owner` in `charter/config.json` **as the base revision has it** (so a change set cannot name its own author the owner; only the install, whose base has no config, reads the config under review) when it makes an owner-only change (`check_owner_commits`); with no `owner` set it warns. A merge commit answers for content no parent had and for any side's change since the merge base that it drops; it is not blamed for an owner change it carries over from the other side. CI also refuses any file under `.charter/` whose SHA-256 differs from `.charter/manifest.json` and warns on the other owned files, the workflow included, whose block comes from the author check (`check_manifest`) (`package/.charter/checks.py`).

**The owner's line** (0.4.12; `docs/design/owner-handover.md`; `tests/test_owner_commit_0_4_12.py`). An agent stages an owner-only change and runs `charter handover`, or the installer does. Either records the handover in `<git dir>/charter/handover.json`: the branch, the message, the paths, and each path's staged blob, with no command and no switch (`record_handover` in `package/.charter/lib.py`). The block it prints ends with one line, `CHARTER_OWNER=1 python3 <root>/.charter/bin/charter owner commit` (`owner_line`). The owner types it after `!` in Claude Code, or in a terminal. `charter owner commit` (`_owner_commit` in `package/.charter/bin/charter`) works in the checkout that holds the engine it names, a worktree included, from any directory. It refuses:

- in a working chain session;
- without a handover;
- inside Claude Code without the switch (`in_claude_code` and `owner_session` in `package/.charter/lib.py`);
- a handover made on another branch;
- a handover overtaken by a commit that touched its paths, which it then drops (`handover_stale` in `package/.charter/lib.py`).

Otherwise it names the paths changed since the handover and those staged but not handed over, then runs `git commit -m <message> -- <paths>`. The pre-commit gate runs as for any commit: the switch, which comes from the owner's line and which the verb never sets, lifts the owner-only check and nothing else. `charter owner` and `charter next` show the line under the staged change once a handover covers it. `charter-pkg fleet --upgrade` records each waiting project's handover (`by: fleet`) and ends with one line, `CHARTER_OWNER=1 python3 <charter>/bin/charter-pkg fleet --commit`, which runs each one's `owner commit`. It names any other handover it finds instead of committing it (`do_fleet_commit` in `bin/charter-pkg`).

**The owner's delegate** (0.4.14; `docs/design/owner-delegate.md`; `tests/test_delegate_0_4_14.py`). Where the config committed on the default branch sets `delegate.level` below `strict`, a watcher outside Claude Code commits some owner acts for the owner after rules and a model judge them (`LEVEL_KINDS` in `package/.charter/lib.py`). Each owner-only change has kinds (`owner_act_kinds` in `package/.charter/checks.py`): `owner-check` and `upgrade` at `routine`, `ruling` at `answers`, `rails`, `scope` and `merge` at `open`, and `structural`, which no level delegates. The layers change as follows:

- **PreToolUse** lets through, with a note, an edit whose kinds the level delegates, read from the committed config, never the tree; an edit whose result cannot be computed is denied at every level (`package/.charter/hooks/pre_tool_gate.py`).
- **Pre-commit** is unchanged for agents: inside Claude Code the agent's commit is refused, so it hands over. The delegate commits outside Claude Code, exactly the recorded blobs through a private index, and runs the gate itself on that index with the engine of its own charter checkout, never the project's hook; outside Claude Code the owner-only check warns, as the owner's own terminal does (`write_commit` in `package/.charter/delegate.py`, `check_owner_only_staged` in `package/.charter/checks.py`).
- **CI** is unchanged: the delegate's commit keeps the owner as author and names itself as committer with a `Charter-Delegate:` trailer (`commit` in `package/.charter/delegate.py`).
- **The hook** denies `charter delegate commit|perform|settle|level <name>` `charter-delegate run` and `charter-pkg fleet --levels` (`--dry-run` aside) to every agent session, read word by word so that a commit message or a grep naming them passes (`delegate_act` in `package/.charter/hooks/chain_gate.py`).

What this cannot do, stated in `docs/review/2026-09-11-weakness-evaluation.md`: a Bash command is not an Edit or a Write, the agent commits under the owner's git identity on the owner's machine, and a pull request can edit the workflow that checks it. The locks are outside the repository: GitHub branch protection with required review, and code owners for the files above (https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners).

## The gates

### Scope (R6): out-of-scope path without an approved change request

- Checks: an edited or staged path matches the `paths:` of an item under `## Out of scope` in `charter/scope.md` and no change request with `status: approved`, `approved_by:` and `approved_on:` lists a glob covering it. Only on `track: client`. Headings are matched ignoring case, hyphens and underscores (`## Out-of-Scope` counts); an item heading without an id (`### Invoicing`) is still gated under its heading (`check_scope` in `package/.charter/checks.py`; `parse_scope` in `package/.charter/lib.py`).
- Blocks: `PreToolUse` deny; pre-commit; CI on the paths changed since the merge base of `--base` (PR base SHA or the push's previous SHA). Files already out of scope before the change set are a warning ("legacy"). When the base is unusable (an all-zero SHA when a branch is created, a SHA a force-push removed), the change set is measured from the merge base with the main line when that is behind HEAD, else from HEAD~1 when the checked-out branch is not the main line (a branch reset to main), and a warning says which (`fallback_base` in `package/.charter/checks.py`, since 0.4.17). Every tracked path counts as changed, with a warning, on a push to the main line itself (a force push may have rewritten more than its last commit), on a detached HEAD, in a clone with no main line, or when git cannot diff from the base (`changed_paths` in `package/.charter/checks.py`; `_check` in `package/.charter/bin/charter`).
- Override: write the change request from `charter/templates/change.md`; the owner sets `status: approved`, `approved_by:`, `approved_on:`. `charter check` refuses `approved` without the two fields (R7). Recorded in `charter/changes/<slug>.md`; the approval is a commit by the owner (`check_changes` in `package/.charter/checks.py`; template `package/charter/templates/change.md`).
- Also: a unit whose `scope:` names an unknown id is refused; a unit with no `scope:` is a warning; a unit whose `perimeter:` reaches an out-of-scope path, or is not covered by the paths of the item it cites, is a warning; `charter check --scope` reports what makes the scope file fail open (no in-scope item, an out-of-scope item without `paths:`, an item without an id, a `###` item under an unknown `##` section) (`check_unit_scope` and `check_scope_file` in `package/.charter/checks.py`).

### Rails (R6 without a devis): open work the road does not name

- Checks: when `charter/rails.md` exists (the path is fixed, so the staged view and the owner-only list both cover it), every open unit names one of its items, with `rail: <id>` or a `roadmap:` link whose `#anchor` is the id (`rails.keys`, by default `rail` and `roadmap`). The first key (`rail:` by default) always decides. A `roadmap:` anchor counts only when it names a known rail, because it links a document section and a section that is not a rail declares nothing. Otherwise the unit is on every rail whose optional `groups` column (comma-separated globs) matches its `group:`, which links a whole plan group without editing each unit. At commit only the units in the change set are judged; `--all` reports the backlog. The file's first table with the columns `id`, `title`, `status`, `order` holds the items; statuses are `todo`, `next`, `in-progress`, `done`, `parked`, `dropped`. An open unit is one whose status is neither in `done_statuses` nor terminal. Such a unit that names no rail, or only ids the file does not list, is a warning. One whose rails are all closed (`done`, `parked`, `dropped`) is also a warning. A duplicate id, an unknown status or a non-integer order in the file is warned (`parse`, `rails_of` and `check` in `package/.charter/rails.py`; `tests/test_rails.py`).
- Blocks: only with `"rails": {"required": true}`, and only for a unit in the change set: pre-commit and CI. A unit written before the rails existed never blocks an unrelated commit (`check` in `package/.charter/rails.py`).
- Override: name an open item. To start work the road does not name, the owner adds an item to `charter/rails.md` first. That commit is the recorded re-plan, and the file is owner-only (`OVERRIDE` in `package/.charter/rails.py`; `package/.claude/rules/charter.md:32`).
- Synthesis: `charter synth` prints the rails in order, each with the units that cite it and their states, then the open units that are off the rails. For a project without a devis, this replaces a hand-kept tracker. A tasket file git ignores is local scratch, not a unit: the gates and the synthesis skip it, because a synthesis citing it fails its anchors in CI, where it does not exist (`taskets` in `package/.charter/lib.py`; `synth_lines` in `package/.charter/rails.py`).
- On the client track the scope gate does the same job against `charter/scope.md`. The two can run together (`package/.charter/rails.py`, `check_scope` in `package/.charter/checks.py`).

### Size (R3): frozen file

- Checks: after the edit, in the staged version, or at HEAD against the change set's base, the file exceeds `limits.file_lines` (800 by default) and grew. Governance files use `limits.governance_lines` (400) **and** `limits.governance_bytes` (32768): one long line counts as one line, so a governance file past either is frozen. The governance set is `governance_files` in `charter/config.json`, globs, by default `CLAUDE.md`, `AGENTS.md`, `charter/scope.md` and `.claude/rules/*.md`; `charter/decisions/*` and `charter/changes/*` are always in it. Globs in `exempt_from_size`, the package's own `.charter/`, and from 0.4.9 the installer's other files (its rules file, skills, agent, workflow, `charter/README.md` and templates), which an upgrade replaces, are skipped (`PACKAGE_FILES` in `package/.charter/checks.py`: the exact paths of `OWNED`, since the manifest is a file a session can rewrite and a glob would also skip a project's own file named like one of them), and so is binary content (a NUL byte in the first 8,000 bytes, the test git itself uses), for which a line count means nothing. A change that crosses 80% of a limit warns to plan a split; later changes above 80% do not warn again. A renamed file is measured against its size under the old name, so a `git mv` is not a new file (`rename_sources` in `package/.charter/checks.py`, 0.4.7).
- Named exceptions: `size_exceptions` in `charter/config.json` lists `{path, lines and/or bytes, because, expires}`. A live entry replaces the limit it names for that one path, so open work can grow a file the owner has budgeted without a split unit. An entry without `because:` or a dated `expires:`, or without a positive budget, is ignored and warned by `charter check`. Expiry is exclusive, as for decisions: on its `expires:` date the entry has stopped, `charter check` warns, and the block message names the date. The file is owner-only, so an agent cannot add or widen an entry (`size_exceptions` in `package/.charter/checks.py`; `tests/test_size_exceptions.py`).
- Blocks: `PreToolUse` deny; pre-commit; CI for a file that grew past the limit in the change set. `--strict` reports every file over the limit, grown or not (`check_size` in `package/.charter/checks.py`).
- Growth slack (opt-in): `limits.growth_slack_lines` in `charter/config.json` (default 0) lets one change add up to that many lines to a non-governance file over its line limit, with a warning. Measured per edit in the session and per commit at the git hook, so several edits that fit one by one can still be refused at commit (`tests/test_gate_noise_0_4_7.py`).
- Override: move code out of the file (shrinking is always allowed), a `size_exceptions` entry the owner writes, or an open unit with `kind: split` that names the file in its `perimeter:` as a literal path; a glob does not count. The owner opens the split unit. While it is open the file may grow (warning only), so the split can be done in steps. Recorded in that unit's `## Log` and `## Evidence` (`check_size` and `split_unit_for` in `package/.charter/checks.py`).

### Done needs evidence (R9)

- Checks: a tasket whose `status` is in `done_statuses` must have a `## Acceptance` checklist (`## Done When`, the Tasket skill's heading, counts too) with every box checked (the refusal names each unchecked box by its AC id, else by its text, 0.4.15) and a `## Evidence` section that names a commit `git cat-file -e` finds or a `$ command` run; a path or a URL alone is refused. Anchors that do not resolve are refused. A unit that has left `next` or `later` cannot remove or rewrite an acceptance line without a new `## Log` line in the same change.
- Blocks: `PreToolUse` deny on the tasket edit; pre-commit and CI for a tasket whose status changes to done in the change set (with `--strict`, every done tasket) (`check_unit_done` in `package/.charter/checks.py`).
- Probes: with `--probe`, or `probes.at_commit` / `probes.in_ci` in `charter/config.json`, the probes of each unit that closes in the change set are run from the repository root with `probes.timeout_s`; a non-zero exit blocks. At commit they run only when the working tree matches the index. `charter probe <id>` runs them on demand and prints the `$ command` lines to paste as evidence.
- The probe record (0.4.15): each probe run leaves a record of its acceptance id, command, outcome (`passed`, `failed` or `timeout`), exit code (null on a timeout), duration, and the ends of its stdout and stderr kept apart, each at most 20 lines and 2 KiB, cut at a line, with each stream's line count (`probe_record` and `TAIL_LINES, TAIL_BYTES` in `package/.charter/checks.py`). 20 lines hold pytest's one `FAILED <test> - <error>` line per failing test for a dozen failures; 2 KiB per stream keeps one probe's record under 4 KiB, half of the 8 KiB a chain handoff may hold (`MAX_LINES, MAX_BYTES` in `package/.charter/chain.py`). Beside the record, the paths changed between the unit's base (the commit the probes before the work run at, `unit_base`) and the working tree, untracked files included, split by the unit's `perimeter:` (all inside when it declares none), without `.taskets/`, `charter/`, `.charter/`, `.claude/` and `.github/` (`changed_since_base`). In a checkout other sessions commit to, their work since the base is in it too. `charter probe <id>` prints the `- `$ command` → result` lines exactly as before, because tele-claude's checker parses them (`_PROBE_LINE`, /home/gui/Projects/tele-claude/services/checker/core.py:98, read 2026-10-13); when a probe fails, a block follows them: `AC-n failed: `<command>` exited N after S s`, each stream's tail on lines that start `  | ` so that none reads as a probe line once stripped, and `changed since <base>, the unit's base: N path(s) inside the perimeter, M outside: ...` (`failure_lines`, `changed_lines`). `charter probe <id> --json` prints `{schema, charter, unit, path, probes: [record], failed: [AC id], changed: {base, inside, outside} or null, findings}`, and `{error}` with exit 1 for an unknown unit; the exit code is the text form's. The gate log row of `charter probe` adds `; failed: AC-2, AC-4` to its detail and a `failed` list (`cmd_probe` in `package/.charter/bin/charter`). The chain's facts print the tails of a closed unit's probe that fails when re-run (`facts` in `package/.charter/chain.py`). Tests: `tests/test_failure_record_0_4_15.py`.
- Probes before the work: when a closing unit's probes pass, each is run again in a detached worktree at the parent of the commit that added the unit's file (at `HEAD` when the file is not committed yet). One that passes there does not test the change: a warning, a block with `probes.base_must_fail`. A criterion whose line contains `(guard)` is skipped, because it protects existing behaviour. The worktree has only tracked files, so a probe that needs untracked dependencies (`node_modules`, a virtualenv) fails there and is not reported; that errs towards letting a weak probe through. A unit added in the repository's first commit has no base and is not checked. Tests: `tests/test_probe_at_base.py`.
- Independent review (opt-in): with `review.required` in `charter/config.json`, done also needs a `- review: <reviewer and model> — <verdict> — <anchor>` line under `## Evidence` whose anchor resolves (a PR comment URL, a commit, a `$ command` run). It is meant for a verdict from a different model family than the one that wrote the code, such as the codex review. It is checked wherever the done gate runs (PreToolUse, pre-commit, CI). The gate checks that the line exists and points somewhere; it cannot check that the review happened, or which model gave it. Tests: `tests/test_review_required.py`.
- Legacy: a tasket listed in `charter/legacy-taskets.txt` (written by the installer from the taskets it found) and without `## Acceptance` closes with a warning, even when it has `## Done When` (`check_unit_done` in `package/.charter/checks.py`).
- Override: none by flag. Keep the status open, or add the evidence. A tasket that must be closed without evidence is `parked` or `skipped`, both terminal for the engines and both honest (`TERMINAL_STATUSES` in `package/.charter/lib.py`).

### Decisions (R1)

- Checks: every `charter:<id>` marker in an edited or staged file names an existing decision (an id ends at a letter or digit, so a sentence's closing period is not part of it); a decision with `status: superseded` or `retired` cannot be cited (the message names `superseded_by`). A file matching an active decision's `binds:` globs without its marker is a warning. Every active decision's `check:` command is run; a non-zero exit is "contradicted". Two files holding one decision or change id are refused. An open unit whose `decisions:` names a missing or retired decision is a warning (`check_decisions_text`, `duplicate_ids`, `run_decision_checks` and `check_unit_decisions` in `package/.charter/checks.py`).
- Blocks: `PreToolUse` deny for a retired citation or a taken id; `PostToolUse` exit 2 (stderr to Claude) when a bound file's check fails after the edit; pre-commit and CI for both. At commit only the decisions whose `binds:` match a staged path run their `check:`; one with no `binds:` runs in CI and in `charter check --all`, not at commit (`tests/test_review_20260923.py`). At commit the checks run in the working tree, so the commit is refused when the working tree differs from the index.
- Override: supersede the decision with a new record that sets `supersedes:`; the owner sets the old one to `superseded` with `superseded_by:`. The new record carries its own `## Because`. Recorded in `charter/decisions/` (template `package/charter/templates/decision.md`; `package/.claude/skills/charter-decision/SKILL.md`).

### Perimeter (R4)

- Checks: the active unit (`CHARTER_UNIT` from the environment, else the one this session chose with `charter unit start`, else the checkout's last choice while it is open and, for a session, only when no session made it: see § The active unit below) declares `perimeter:` globs; an edited or staged path outside them, outside `.taskets/`, `charter/` and `.charter/`, and not named under the unit's `## Outside perimeter` section. A file that git ignores and does not track, such as a tool's local journal, is never the unit's work and is not checked (0.4.4, `lib.ignored`) (`check_perimeter` in `package/.charter/checks.py`).
- Blocks: `PostToolUse` warning in session; pre-commit block on the client track, warning on the prototype track; CI does not know the active unit and does not check this (`check_perimeter` in `package/.charter/checks.py`).
- Override: the note itself (`- path: why`), or widening `perimeter:`. No active unit is a warning ("edits are not attributed"), never a block (`check_perimeter` in `package/.charter/checks.py`).
- Another session's path (0.4.15): the index is the checkout's, so a plain `git commit` takes what any session staged. At commit, a staged path outside the perimeter that another live session's record lists as edited, and the committing session's does not, is named as that session's, at the same level: `<path> is staged, but session <id> edited it and this session did not; a plain `git commit` charges it to unit <id>`, with the override to commit only this session's paths (`git commit -m <message> -- <your paths>`; with a pathspec, git gives the hook only those paths). The records are the hooks' `<git dir>/charter/session-<id>.json`, removed at SessionEnd; they list Edit, Write and NotebookEdit, not a file a Bash command changed (`edited_by_other_sessions` in `package/.charter/checks.py`). The gate log rows of `charter check` carry `session` when it runs from a session (`cmd_check` in `package/.charter/bin/charter`).
- The active unit (0.4.15): `charter unit start` records in `<git dir>/charter/active.by` which session made the checkout's choice, empty when none did (the owner's terminal, an engine). A session with no unit of its own inherits the checkout's choice only when no session made it; a choice made by another session, or recorded before 0.4.15, is not its own, and `charter unit show` says so: `no active unit (the checkout's last choice, <id>, is another session's; ...)`. Outside a session (no `CLAUDE_CODE_SESSION_ID`: a terminal, CI) the checkout's choice applies as before (`inherits_checkout` and `active_unit_source` in `package/.charter/lib.py`). Until 0.4.14 a session inherited any open choice; in tele-claude four sessions of 2026-10-08 ended charged to one unit, and a commit tagged for one unit was warned against the next one's perimeter (`docs/bugs/2026-10-02-concurrent-sessions-in-one-clone-share-one-active-unit.md`).
- Perimeter fit (0.4.15, a report, never a gate): for a unit, the files its commits touched outside its `perimeter:` (and how many of them are named under `## Outside perimeter`), and the perimeter entries no commit touched. A commit counts for a unit when its subject says `unit <id>`, as in `(unit <id>)` or `(#105, unit <id>)`, the tag `package/.claude/skills/charter-unit/SKILL.md` asks for (65 of tele-claude's 371 commits since 2026-09-26 carry one); a tag that is the start of exactly one id followed by `-` counts for it, one that starts two or more ids counts for none, and so does a subject that names two or more units, or one unit beside such a tag, since its files cannot be shared out. A tag that names no unit, such as `unit tests`, is passed over. The body is not read: a squash merge lists there every unit it carries, and in tele-claude one such commit would have charged 107 files to each of 12 units. One pass over the commits of `HEAD`, merges left out; the exempt paths above are not counted as touched, but they do touch an entry such as `.taskets/**` (`perimeter_fits` and `fit_text` in `package/.charter/checks.py`). It cannot see work committed under no tag or under another unit's tag, a squash merge's units, work not yet committed, or commits on a branch `HEAD` does not contain. On tele-claude's history on 2026-10-13 it read 51 units with commits and a perimeter: 251 of 290 entries touched (mean per unit 0.88), and 28 files outside in 18 units, 17 of them tests, all 28 noted (`docs/session-log.md` § 2026-10-13). `charter unit show <id>` prints it (`perimeter fit: ...`), `charter unit show <id> --json` has it as `perimeter_fit: {commits, touched, outside, outside_noted, entries, untouched_entries}`, and `charter synth` has one line per unit that a commit names, under `## Perimeter fit`.

### Memory (R8)

- Checks: an active decision without `## Because` or without `expires:`; a dated `expires:` on or before today, because expiry is exclusive and a decision stops applying at the start of that date; a dated `expires:` that is not later than the decision's `date:`; a `kind: lesson` without `owner:`. The boundary is the one tcv2's HARNESS.md uses for `expires_on` (https://github.com/elgui/tcv2/blob/936cb5618bdb98453b4a73e167670bccc74a27a5/services/harness_evidence.py).
- Warning only, in `charter check --memory` and CI output (`check_memory` in `package/.charter/checks.py`; `package/.github/workflows/charter.yml:18`).

### Stop gate (R9/R10 in the session)

- Judges only a turn that attempted an Edit or Write or moved HEAD; an explanation is not a completion claim (`package/.charter/hooks/stop_gate.py`).
- Checks: `last_assistant_message` contains a completion claim (done, complete, implemented, fixed, shipped, tests pass, a check mark) and no commit, `path:line` or `$ command` run, and does not admit "not done" or "unverified"; or the active unit is `done` and fails the done gate.
- An anchor that does not resolve from this checkout (a file and line with no directory, a file or a SHA in another repository) is a warning: logged as `anchors/warn` and told to Claude through `additionalContext`. A claim that cites no anchor of any kind still blocks (0.4.7, `package/.charter/hooks/stop_gate.py`).
- Blocks once. The second Stop in the same turn passes through and logs `done/passed`. Reason text names what to cite. When a commit landed during the turn and the active unit's `## Log` did not move, `additionalContext` asks Claude to append the line; this costs one short continuation (`package/.charter/hooks/stop_gate.py`).

### Anchors (R10)

- Command: `charter anchors <file>...`, exit 1 on any unanchored claim line or unresolved anchor. Definitions in `docs/method.md` § Accepted results. Exempt sections: `<!-- charter: opinion -->` ... `<!-- charter: /opinion -->`. Admitted claims, by evidence class (`docs/method.md` § Evidence classes): reported `(reported in ...)`, `(operator report ...)`, `(claimed by ...)`, `(outside this repository ...)`, `(in the scratchpad ...)`, `(in the clone ...)`, `(on the test bed ...)`; inference `(inference ...)`, `(unverified)`, `(not verified)`, `(estimate ...)`, `(to be confirmed)`.
- `charter anchors --pr <file>` is the pull-request mode: `#123` and `owner/repo#123` count as anchors, an empty description is reported, and the result is a warning (exit 0). On the prototype track every anchors result is a warning.
- Runs in CI on `charter/progress.md`, `docs/progress*.md`, `docs/report*.md` (hard), and on the PR body in `--pr` mode, re-run when the body is edited. Not on decisions or the scope, whose statements are normative.
- `charter synth` runs it on its own output and refuses to write on failure. The written synthesis leaves out gate activity, which lives on one machine.

### Chain budget and hand-over (0.4.9)

For sessions of a continuous chain (`docs/design/continuous-chain.md`), all in `package/.charter/chain.py`, wired by `package/.charter/hooks/chain_gate.py`:

- **Join** (`UserPromptSubmit`, `on_prompt`): a prompt carrying the line `charter-chain: <id> session <n>` attaches its session to that link of the chain and receives `.charter/chain-rules.md` verbatim as `additionalContext`. A link already joined by another session or already closed (a tab that started after `chain resume` moved on), a chain that is not running, or rules whose SHA-256 differs from the one recorded at the start (the chain halts) get a refusal to work instead.
- **Usage** (`PostToolUse`, `on_post_tool`): the context is the last main-chain response's input, cache and output tokens in the transcript, plus a quarter of the tool result's characters (`context_tokens`); the session is told its share every 5 points, and to hand over on every call past `wrap_pct`.
- **Cap** (`PreToolUse`, `on_pre_tool`): past `cap_pct`, every tool is denied except Write or Edit of the session's own handoff or of `.taskets/*.md`, and Bash commands whose every part is `git ...` or the charter CLI (`allowed_at_cap`). The command is read with shell quoting (`plain_commands`): commands joined by `&&`, `||`, `;` or newlines pass, and a redirection, a pipe, `&`, a subshell, a backquote or `$(...)` outside the `"$(cat <<'EOF' ... EOF)"` message form refuses it; a quoted commit message may hold `<`, `>` and several lines. A `git` command that sets config on its line (`-c`, `--config-env`), `--exec-path` or `git config` is refused, since an alias such as `-c alias.x='!cmd'` runs a shell command (`_git_runs_more`). In the tab trial a regex over the raw line refused a commit whose `Co-Authored-By: Name <address>` trailer it read as a redirection (`docs/trials/2026-10-04-chain-tab.md`). The refusal names what passes. `AskUserQuestion` is denied at any usage: the halt is the question.
- **Start-up** (`on_pre_tool`, `cmd_next`, `started_past_line`): the usage at a session's first tool is recorded as its start-up (`start_pct`, `start_tokens` in `link.json`). A session that hands over `continue` after a start-up at or past `wrap_pct` halts the chain, since every session starts the same way; `charter chain resume --window`, `--wrap`, `--cap` sets a new budget for the sessions that follow. `charter chain start` warns when the hand-over line is at or under the start-up measured in this repository's latest chain, else an estimate by launcher (`measured_startup`).
- **Stop** (`on_stop`): a chain session that has not been closed by `charter chain next` is blocked, with a reason that depends on its budget. The third consecutive Stop with no tool call between is let through and recorded as `stalled`; the chain then waits for the owner.
- **Closed** (`on_pre_tool`, `CLOSED_GIT_RE`; `tests/test_owner_gate.py`): once `charter chain next` has closed a session, and until the chain completes, the hook denies it Edit, Write, MultiEdit and NotebookEdit, and any Bash command that starts a `git` verb that changes files, the index or the branch (`commit`, `add`, `reset`, `checkout`, `push`, `clean`, `stash` and the like). The command check is best effort: a git alias, `bash -c` or a script gets past it (cross-review, 2026-10-05). The tab of a completed chain's session is an ordinary session again. In the owner-gate re-check a closed session committed 3 s after its close, past the commit the chain waited at, unseen by its facts and by the next session (`docs/trials/2026-10-05-owner-gate-recheck.md`). Reading, and a repeated `chain next`, still pass. A file write by another Bash command is not caught here, but it leaves the tree dirty, and a resume refuses a dirty tree.
- **Hand-over** (`charter chain next`, `cmd_next`): refuses a handoff that fails `check_handoff` (frontmatter, sections, an anchored `## Verified` from session 2 on, commits that resolve, 80 lines and 8 KiB at most), uncommitted changes its `## State` does not name, any uncommitted change with `status: wait` or `complete`, `status: wait` without `## Wait` or without a valid `owner.md` (§ The owner's acts), with a `## Wait` that gives commands of its own after `run:` (they belong in `owner.md`, 0.4.11), or with a backticked `## Wait` command or an `owner.md` command that holds a `<placeholder>` (`placeholders`, `package/.charter/chain.py:459`, and `validate` in `package/.charter/owner_acts.py`: zsh reads `<bucket>` as a redirection; `sort < in.txt` and `<<EOF` pass), and a `continue` below the hand-over line when nothing was committed, or below half of it, without `--early`. Two sessions in a row that changed nothing outside `.taskets/` and checked no criterion halt the chain as stalled (`stalled`); in the tab trial any commit counted, a `## Log` line included. A second `chain next` that waited on the chain's lock finds the session closed and launches nothing.
- **Wait** (`cmd_next`, `_hand_over`, `notify`, `owner_items`): `status: wait` sets the chain to `waiting` and tells the owner (a macOS notification unless `chain.notify` is `off`, and `chain.notify_command`). `charter owner` and `charter next` list the chain's acts from one function (`owner_steps`, `package/.charter/chain.py:841`): with `owner.md` (0.4.11), each act with Codex's note on it, then `charter owner run` and `/resume-chain ok`; for a wait handed over before 0.4.11, its `## Wait` lines. Each command to paste stands alone on a line, so that a triple-click copies it whole: `charter owner run`, or each command a `## Wait` act gives after `run:` (`run_lines`, `package/.charter/owner.py:209`; the `run` field in `--json`, 0.4.10). The notification says how many acts wait and names `charter owner`, and with `owner.md` `charter owner run`, instead of a cut of the acts (`_wait_note`, `package/.charter/chain.py:739`). At a wait, `chain next` prints the same acts verbatim, each command the owner pastes in a fenced block (with `owner.md`, `charter owner run`; an act's own command shows as a `$` line, since the run executes it), the resume line and `charter owner`, for the session's closing message to copy (`_hand_over`, `package/.charter/chain.py:1292`); the rules say the closing message gives exactly that, never a summary (`package/.charter/chain-rules.md` § 4). `chain start` refuses while a chain waits; `chain stop` ends a waiting chain, and a stop requested before a session waits wins over the wait. The resume (§ The owner's resume) takes the chain's lock and refuses from a branch other than the chain's, on a branch that lost the last session's commit, and, for a waiting chain, with uncommitted changes other than the owner's ticks it closes, printing the commit to make first. An untracked file that existed at launch counts as uncommitted once it is edited or deleted.
- **The owner's acts** (`package/.charter/owner_acts.py`, 0.4.11; `tests/test_owner_acts_0_4_11.py`): a session that waits writes every act into `owner.md` beside its handoff, from `charter/templates/owner.md`: a numbered `## <n>. <title>` per act, `closes:` with the open `— owner:` lines it closes (`<unit> AC-n`, or `<unit> "<text>"` for a line without an id), and either a command in one fenced block (`expect-exit:`, `expect-output:`, `stop-on-fail:`, `timeout:`) or `do:` with an optional `check:` command; `later: yes` marks an act that blocks nothing now. `chain next` refuses an `owner.md` that does not parse, closes a line that is not open, or names no unit (`validate`). It then has the file reviewed (`review`): `chain.owner_review` is `auto` (Codex when `codex` is on PATH, the default), `codex`, `off` or a command template with `{prompt}`, `{schema}` and `{out}`; `CHARTER_OWNER_REVIEW` overrides it. Codex runs `codex exec -C <root> -s read-only --ephemeral --output-schema`, at `chain.owner_review_effort` (`medium`) and for at most `chain.owner_review_timeout_s` (300); its verdict per act (class, risk, reversible, what it touches, what to read, whether it does more than its title says) lands in `owner-review.json`, pinned to the file's SHA-256 and reused while the file is unchanged. An act it classes `agent_can_do` refuses the hand-over unless the act says `owner-because:` (`sent_back`). A review that cannot run is recorded with why, and the wait goes on. The hand-over records `owner_sha` in the session's `link.json`. `charter owner run [--only N,M] [--yes] [--id ID]` runs the acts of the waiting chain's last session in order, each with `zsh -c` (as the paste-ready standard writes for) at the repository root, the owner's terminal as its stdin, so `sudo` and a `read` ask there; it refuses an `owner.md` whose SHA-256 is not `owner_sha`, a chain that is not waiting, and a working chain session (`_owner_run` in `package/.charter/bin/charter`). At a terminal (`/dev/tty`, as sudo reads it), an act Codex rates high risk asks `y/N` first, and a manual act without a `check:` asks "Done?"; without one nothing is asked. A `timeout:` kills the act's shell and every process under it, and an act killed by a signal never passes; once the shell has exited, a process it left holding the output does not hold the run. Each act's outcome is saved as soon as it ends, so a Ctrl-C keeps what ran. Each act's outcome (passed, failed with its exit and the end of its output, declined, skipped after a failed or declined `stop-on-fail` act, later, unasked) goes to `owner-run.json`, and its full output to `owner-run.log`. The hook denies, in every session, a Bash command that runs `charter owner run`, its options in any order (`OWNER_RUN_RE` in `package/.charter/hooks/chain_gate.py`); the owner's `!` command is not a tool call, and no PreToolUse hook sees it (https://code.claude.com/docs/en/hooks-guide).
- **sudo in a chain session** (`sudo_asks`, `on_pre_tool` in `package/.charter/chain.py`, 0.4.11): the hook denies a working chain session's Bash command that runs `sudo` where a command starts (after a separator or a newline, `if`, `!`, `{`, `$(`, `env`, `nohup`, `timeout N`, or inside `sh -c '...'`) without `-n` (or `--non-interactive`) among its options, since it would put a Touch ID or password prompt on the owner's screen that they did not start; in hermes-custom's chain of 2026-10-05, session 2's probes through `conf` raised one each, and an unanswered one timed out after 120 s (outside this repository: its `s02/handoff.md`, `## Watch out`). `sudo -n` runs what the machine's sudoers allows without a password. A script or a probe that calls `sudo` inside is not seen; the chain rules (§ 5) say to put such a command in `owner.md`.
- **Owner verbs** (`_owner_verb` in `package/.charter/bin/charter`, `on_pre_tool`): `charter rule`, `approve` and `rail` refuse inside an open session of a running chain, found by `CLAUDE_CODE_SESSION_ID`; and the hook denies a chain session's Bash command that runs one of them or names `CHARTER_OWNER` (`OWNER_ACT_RE`), which no unset variable gets around. In every other session of the project, the hook denies a Bash command that names `CHARTER_OWNER` (`package/.charter/hooks/chain_gate.py`). A script that calls the package's functions itself is not caught; the chain rules forbid it.
- **The owner's resume** (`owner_prompt`, `owner_resume`, `typed_by_owner`, `parse_resume`, `owner_ticks` in `package/.charter/chain.py`; `tests/test_owner_gate.py`): a paused chain (waiting, halted, stopped, stalled) resumes only when the owner types `/resume-chain [<id>] [--window N] [--wrap N] [--cap N] [--more N] [--skip-review] [ok | skip | AC-n | <unit>:AC-n ...] [note]` in an interactive Claude Code session of the project. The hook catches it on `UserPromptSubmit` (the raw prompt) or `UserPromptExpansion` (the command's name and arguments), performs the resume, and answers `{"decision": "block"}`, so the model never reads the prompt and the owner reads the outcome (https://code.claude.com/docs/en/hooks). `ok` closes the open `— owner:` lines whose acts passed in the owner's last `charter owner run` (a command or a `check:` that passed, a manual act confirmed or not asked), and keeps open those of an act that failed, was declined, skipped or not run, or is `later`; while `owner.md` holds a command or a `check:` and nothing was run, `ok` is refused with the command to run (`resume_plan` in `package/.charter/owner_acts.py`, 0.4.11). For a wait handed over before 0.4.11, without `owner.md`, `ok` closes every open `— owner:` line of the units the wait names. `skip` closes none; while such a line is open, a resume with neither and no `AC-n` is refused with the lines and the acts listed, so the owner never needs a line's id (the owner, 2026-10-04). The leading `AC-n` close those open `— owner:` lines of open units in one commit made as the owner (the owner switch set for that commit alone, as the owner verbs do), against the committed text, so a box the owner ticked by hand is closed by naming it; a line that is not an open owner line, or that two units hold, refuses the whole command, and nothing changes. The rest is the note, verbatim; the next briefing carries it with the lines closed (`last_resume` in `chain.json`). An owner line that a commit other than the resume closed since the chain paused (the owner's own terminal, or an agent past the gates) is named in the outcome and in the next briefing, which tells the session to reopen each one the owner's note does not claim (`closed_outside`). Every other commit made since the chain paused, other than the resume's own, is named in the outcome too, and the next briefing asks the session to read each one before building on it (`commits_since`). It is refused in a headless session (`CLAUDE_CODE_ENTRYPOINT` starting with `sdk`, or `CLAUDE_CODE_SESSION_ATTENDED=0`) and in a chain session that is still working. In a chain session that has handed over it goes through: that tab is where the owner lands, and nothing types there after the launcher's first prompt (0.4.11, `typed_by_owner`). The refusal in a working chain session, and the wait's entry in `charter owner` and `charter next`, print the command that opens a session of the owner's own, `cd <root> && claude`: the owner typed the command in the chain's tab four times in two trials (`own_session`; `docs/trials/2026-10-05-owner-gate-recheck.md`), and twice more in hermes-custom's chain of 2026-10-05 (outside this repository: its session 1 transcript). `charter chain resume` refuses everyone and prints the command to type (`cmd_resume`). The command file, `.claude/commands/resume-chain.md`, sets `disable-model-invocation: true` (https://code.claude.com/docs/en/skills), and its body only says the hook did not catch the command. The hook's timeout on these two events is 900 s: a resume after a stall closes the session first, which re-runs the gates and the probes, then launches the next session's tab. A prompt with no session id is refused. If the launch fails after the owner's lines were committed, the outcome reads `partly done`, and the next resume keeps those lines for the briefing.

### Chain groups and their review (0.4.9)

For a chain whose `chain.review` is not `off` (`docs/design/continuous-chain.md` § Groups and their review), all in `package/.charter/chain_groups.py`:

- **Unit start** (`charter unit start`, `unit_start_refusal`, called from `cmd_unit` in `package/.charter/bin/charter`): in a chain session (`CLAUDE_CODE_SESSION_ID` joined to a running chain), a unit whose group has not started is refused, with the hand-over to make instead. Units of the current group and of earlier groups start as always. Outside a chain session nothing changes, and an error in the check allows and is logged.
- **End of a group** (`charter chain next`, `advance`, `ends_group`): a `continue` whose `next_unit:` is in a group that has not started, or a `complete`, starts the group's review instead of the next session, and is never refused as early. The review is `codex exec review --base <start> -c model_reasoning_effort=<effort> -o <file>` in a detached worktree at the group's last commit (`run_review`, `review_command`), at `<tmp>/charter-review-<repository hash>-<chain id>/tree`; what a runner killed before its cleanup left there is removed before the chain's next review. A review that cannot run, returns nothing, or runs past `chain.review_timeout_s` halts the chain. The runner records the outcome under `chain.lock`, which `charter chain stop` and the recording half of `charter chain next` also take (`chain_lock`, `_hand_over`), so none writes back a stale `chain.json` over another's.
- **Resume after a broken `complete`** (`on_resume`): a chain halted because the session that said `complete` left failing probes or blocking gates resumes with a repair session, not with the last group's review.
- **Answers** (`charter chain next`, `check_review`): the handoff of the session that answers a review is refused until its `## Review` has one line per finding that starts with the finding's id and its answer: `R<n> fixed <commit>` with a commit after the reviewed range and on the chain's branch (an ancestor of HEAD), or `R<n> dismissed <path:line or $ command> <why>`. A handoff with `status: halt` or `wait` is not held to it; the session after the owner's answer gets the whole review again (`on_resume`).
- **A group ends at a commit** (`charter chain next`, `needs_commit`): at a group's end, at `complete`, and when the answering session hands over, an uncommitted change is refused even when `## State` names it, because the review reads the commit and the owner merges up to it.

## Git hook

`package/.charter/githooks/pre-commit` runs `python3 -B .charter/bin/charter check --staged`. It reads `charter/` and `.taskets/` from the index (`lib.index_view`), so the commit is judged, not the working tree. Activated by `git config core.hooksPath .charter/githooks`, which is repository config and is not cloned: `python3 .charter/bin/charter setup` sets it in a clone, the installer sets it on every run, and the SessionStart banner says when it is missing. A project that already runs git hooks (lefthook, pre-commit, husky, scripts in `.git/hooks`) keeps them: the installer and `setup` then leave `core.hooksPath` alone unless `--replace-hooks`, and the gate runs as `python3 -B .charter/bin/charter check --staged` from the existing framework (`package/.charter/githooks/README.md`). A relative `core.hooksPath` resolves inside linked worktrees, verified in the trial (G7). `git commit --no-verify` skips it; CI runs the same checks.

The gate fails open on its own errors. `charter check` and `charter anchors` catch any unexpected exception: they print one line to stderr, log `error/error` (`charter log`), and exit 0, so the commit goes through ungated. A `charter/config.json` the gates cannot read is not such an error: since 0.4.3 it is refused (§ Config). Binary files are read without decoding errors and skipped by the size and decision checks.

## CI

`package/.github/workflows/charter.yml`: on pull requests (opened, edited, synchronize, reopened) and pushes to `main` and `staging`. It fetches `refs/pull/*/head` so an evidence commit a squash or rebase merge removed from the branch still resolves (GitHub documents fetching `pull/ID/head` and keeping a closed pull request's head branch restorable: https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/checking-out-pull-requests-locally, https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-branches-in-your-repository/deleting-and-restoring-branches-in-a-pull-request). Then `charter check --all --ci --base <sha>` where the base is the PR base SHA or the push's previous SHA; `charter anchors` on syntheses and reports; `charter anchors --pr` on the PR body. Probes run only when `probes.in_ci` is set, because the runner has Python 3 and nothing else unless the project installs its test dependencies in the workflow.

A gate that crashes in CI fails open as it does at commit: the step passes, so a crash never blocks a merge. When `GITHUB_ACTIONS` is `true` it also prints a `::warning` workflow command, which puts the error on the run's summary (https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands, "Setting a warning message"; https://docs.github.com/en/actions/reference/workflows-and-actions/variables, `GITHUB_ACTIONS`). The runner's gate log is gone when the job ends, so that annotation is the only trace.

## What a gate cannot see

- A `PreToolUse` hook does not run for an Edit whose `old_string` is absent from the file: Claude Code rejects that Edit first (trial T1c). It does not run for files added with `@` in a prompt, nor for files changed by a Bash command; the git hook and CI see those.
- The perimeter gate depends on the session declaring its unit. Nothing forces `charter unit start`; the log shows unattributed edits and the SessionStart banner says so.
- A commit is charged to a session's unit through `CLAUDE_CODE_SESSION_ID` in the git hook's environment. A `git commit` run by a session's Bash tool passes it to the pre-commit hook (measured 2026-10-13, `docs/session-log.md` § 2026-10-13); a commit made from a terminal has none and reads the checkout's choice, whoever made it. A path another session changed by a Bash command is not in its record, so it is charged like this session's own (`edited_by_other_sessions` in `package/.charter/checks.py`).
- The done gate checks that a commit is named or a run is recorded, and with probes enabled that the probes pass and did not already pass before the unit. It does not check that they test the criterion: a probe that fails before for an unrelated reason, or a criterion marked `(guard)` without cause, passes. The reviewer agent and the owner check the truth.
- The scope gate matches paths. Work that is out of scope but lands in an in-scope path is invisible to it; the unit's `scope:` and the owner's review carry that.
- A permission denial (`--permission-prompts none`) and a gate denial read alike to the agent. The log distinguishes them.
- A `check:` is a shell command read from a markdown file and run at every commit and in CI. That is the feature; the SessionStart banner lists every one.
- Most of R7's operational commitments are actions, not files: a deployment, a change to production data or schema, a purchase, a public release, another person's work, a merge into main. No gate sees them; the rules file carries them. Widening a permission is gated where it is a file, since `.claude/settings.json` and `.claude/settings.local.json` are owner-only.

- The chain's budget is measured from Claude Code's transcript, whose format is internal and may change between releases (https://code.claude.com/docs/en/sessions); on a transcript it cannot read, the budget gate allows. The window size is not in the transcript, so it comes from the model name (`[1m]`) or `chain.window_tokens`.
- The cap lets every `git` command through, because committing is part of handing over; a session past the cap can still run `git` for other ends (`git checkout <sha> -- <path>` writes the tree, and an alias or a hook already in the repository's config runs what it runs).
- The start-up is measured at the first tool, so it includes the session's first response. Start-up differs by launcher (about 32,000 tokens headless, 49,500 in a cmux tab, on 2026-10-04), and `measured_startup` takes the latest chain's figure whatever its launcher.
- A session that edits a unit already `done` without reopening it is not refused; the facts show it as `done -> done` (`docs/trials/2026-10-04-groups.md`).
- Whether a session verified its predecessor's evidence truly is a judgment: `chain next` checks that `## Verified` cites a run, and re-runs the probes itself, but not that the session read the code.
- The owner's resume trusts the prompt. A program that types `/resume-chain` into an interactive tab (`cmux send`, `tmux send-keys`, `osascript` keystrokes, the spawn shim's briefing) reads to the hook as the owner, and the hook input has no field that tells typing from injected input (https://code.claude.com/docs/en/hooks). The headless refusal reads `CLAUDE_CODE_ENTRYPOINT` and `CLAUDE_CODE_SESSION_ATTENDED`, which Claude Code does not document and set over the caller's values in `claude -p` on 2.1.289 (`docs/trials/2026-10-04-owner-gate.md`); a release that changes them turns the refusal off. An agent that writes `.git/charter/chain/<id>/chain.json` or the engine by hand, or whose script imports the engine and calls the resume itself (`owner_resume`, cross-review of 2026-10-04), resumes the chain past the gate: the gate holds the paths a session is given, not a process of the owner's account that sets out to go round it. The engine edit shows as an owner-only `.charter/**` change at commit and in CI, and a line it closed shows at the owner's next resume (`closed_outside`).
- The review of the owner's acts is advice, and its record is a file. A session can rewrite `owner-review.json` or `owner-run.json` by a Bash command after its hand-over, as it can any file under `.git/charter/`; `owner_sha` catches an `owner.md` changed after the review, not a forged review or run. A forged run can only make `/resume-chain ok` close fewer lines than 0.4.9's `ok` did, which closed every waited line (`resume_plan` in `package/.charter/owner_acts.py`). Codex reads the repository under `-s read-only`; a prompt injection in a file it reads can shape its note, never run anything or close a line. `charter owner run` runs what an agent wrote with the owner's rights, as pasting it did: it shows each act's note first, and asks for a high-risk act only at a terminal. The hook's match on `charter owner run` is a pattern: an alias or a script that runs it gets past, and the chain rules forbid it; it also denies a commit message or a grep that spells the command, since a quoted path still runs. The sudo check denies the same way a quoted text that reads like a command (`git commit -m "a; sudo b"`).
- An `— owner:` line is the owner's at the Edit gate, at commit inside Claude Code and in CI, which checks the author. A Bash command that edits the file is not an Edit; a commit outside Claude Code only warns, since the committer cannot be told apart from the owner; and CI checks the author name or email, which is the repository's git user for an agent's commit as for the owner's. In a session of another project, whose hooks are not this project's, nothing denies `CHARTER_OWNER=1` or an unset `CLAUDECODE`, and a command that spells either name another way, or a script file that sets it, gets past the hook in this one; the hook reads Bash commands only. The hook denies any command that names either variable, a `grep` included. An owner line without an AC id is known by its text, so rewording it counts as closing it, and deleting a whole unit file is not read as closing its lines.
- The handover record is a file under `.git/charter/`, and a Bash command can rewrite it after the handover, as it can any file there. The owner's line commits what the record names, and prints the message, the path count, the paths changed since the handover and those left out before it commits. The record holds no command, and the gate still runs at the commit (§ Owner-only changes, The owner's line). The hook's denial of `charter owner commit` is a text match, like its denial of `charter owner run`. What keeps an agent from making the commit is the owner switch, which the verb never sets: without it, inside Claude Code, the verb refuses, and so does the pre-commit gate.
- A review answer is checked for its form, not its truth: `dismissed` needs a `path:line` or a `$ command`, not a correct one, and the next session's verification is what judges it (`check_review` in `package/.charter/chain_groups.py`). The answering session's fixes are not reviewed by Codex again.
- The group boundary holds at `charter unit start`. What goes round it is named in the facts of the hand-over, not refused: a unit of a group that has not started that moved, a unit whose `rail:` or `group:` changed in the session, and a changed path that only units of later groups name in their perimeter. A change to a path that a unit of the current group also covers (a shared `tests/**`) is not named (`crossing` in `package/.charter/chain_groups.py`).

## Config

`charter/config.json` is read by `load_config` and `config_from` in `package/.charter/lib.py`, against `CONFIG_SCHEMA` there: the keys each section may hold and the type of each value. Before 0.4.3 any key was merged, so `{"rails": {"requird": true}}` left `rails.required` off and a track of `"prototpe"` switched the scope gate off (outside review, 2026-09-24; `tests/test_config_0_4_3.py`). Now:

- An unknown key, at the top or in a section, is not applied. The message suggests the nearest known key: ``unknown key `rails.requird` (did you mean `required`?); ignored``.
- A value of the wrong type keeps its default. JSON `true` is not accepted as a number.
- A track other than `client` or `prototype` is read as `client`, the stricter track.
- A file that is not JSON, or not a JSON object, leaves every setting at its default, track `client`.

Each of these is a `charter/config block [charter/config.json]` finding in `charter check`, so the commit that introduces it is refused at the git hook and in CI, with the override "the owner corrects charter/config.json". The config is judged as staged, like the rest of `charter/`. The SessionStart banner prints each problem with "Commits and CI are refused until the owner corrects it"; the session hooks keep running on the values that were applied. `python3 .charter/bin/charter config` prints what the gates read, `track <track>, opt-ins: <list or none>`, then one `problem:` line per problem, and exits 1 when there is one.

`delegate.level` is `strict`, `routine`, `answers` or `open`; another value is a problem and reads as `strict`. The gates never read it from the working tree: `delegate_level` reads the config committed on the default branch, and a branch's own committed level only when it is stricter (`package/.charter/lib.py`). Local refs are an agent's to move, so the watcher also reads the level on the repository's default branch on GitHub and acts on the stricter of the two (`github_level` in `bin/charter-delegate`); a level set locally counts once it is pushed (`docs/design/owner-delegate.md` § Where the level is read).

The opt-ins are `rails.required`, `probes.at_commit`, `probes.in_ci`, `probes.base_must_fail` and `review.required` (`OPT_INS` in `package/.charter/lib.py`). The ones that are on appear in the banner and at the end of every `charter check` summary line, `[staged, track client, opt-ins: review.required]`, so a CI log shows what it enforced.
