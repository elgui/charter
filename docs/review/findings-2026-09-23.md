| # | Finding | Fix | Pinned by |
|---|---|---|---|
| 5 | The owner-variable rule in `owner_only_changes` applied to every path, inside the project or not. It exists because a settings `env` block reaches the running session; a scratch file outside the project reaches nothing, and the gate made the session spell the name around it (tcv2 #97's PR body). | The rule applies when `reaches_the_session(rp)` holds: anything inside the project, and a Claude Code settings file anywhere by name (`settings.json`, `settings.local.json`, `managed-settings.json`, `managed-settings.d/*.json`), checked on the path and on its link target. Matching by name refuses a scratch file that happens to be called `settings.json`; that costs a rename, where missing a settings file would switch the owner checks off. Shell rc files (`~/.bashrc` exporting the variable) are not gated, and should not be: the hooks inherit Claude Code's environment, not a new shell's, so an rc file reaches only a session started after it, which the owner starts.

## Not fixed

- **An unusable CI base blocks every file** (tcv2 #92 review, pass B). When `--base` is an all-zero or unreachable SHA, for example on a first push or a force push, every tracked path counts as changed. On tcv2 at #92's head that is `266 blocking` (`charter check --all --ci --base 0000…`), from pre-existing oversized files and legacy done taskets. `docs/gates.md` documents the warning but not the blocks. tcv2 never force-pushes `main`, so it has not fired. The remedy is a design choice: fall back to the default branch's merge base, or downgrade to warnings when the base is unusable.
- **The owner check trusts git identity.** Author name and email are set by the committer. That is already stated in `docs/gates.md` § Owner-only changes ("What this cannot do"), with branch protection and code owners as the lock outside the repository. It is not a new finding.
- **66473b7 review, P1** (a non-rail `roadmap:` anchor beat the `groups` column): already fixed by 6da4d88, whose `rails_of` uses a `roadmap:` anchor only when it names a known rail.
- **6da4d88 review, P2a** (`check --all --ci` still lists backlog units off the rails): documented ("`--all` reports the backlog"), and those findings are warnings, because `level` is `block` only for a unit in the change set (`package/.charter/rails.py`, `check`).

## The flaky test

A run of the README command failed once on 2026-09-23 and passed on the next 3 (operator report in the tcv2 handoff). It did not reproduce in 9 more runs: 5 sequential runs of the README command (71–77 s each), then 4 in parallel under `PYTHONHASHSEED` 1–4. No `FAIL:` block was captured. The two time-sensitive tests are the suspects:

- `test_review_regressions.py::…test_rework_counts_sessions_after_the_first_done` orders session ends against a commit time, with `time.sleep(1.1)` between them;
- `test_batch1_regressions.py::ExclusiveExpiry.test_a_decision_expiring_today_is_expired_and_one_expiring_tomorrow_is_not` compares `date.today()` in the test with `today()` in a subprocess, which disagree for a run that crosses midnight.

Next time it fails, keep the `FAIL:` block.
