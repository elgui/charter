# Project Road: preparation through supervised execution

Integration design, 4 November 2026. The acceptance scenarios and delivery sequence below are proposed Tele-Claude work. This document changes no Charter package, gate, authorization or installed project. The capability inventory distinguishes code already present from that proposed work (`AGENTS.md:3`, `package/VERSION:1`).

<!-- charter: opinion -->
As a project owner, I can understand the road and its dependencies, see what is missing, strengthen specifications and acceptance, select a coherent set of rails, inspect what a run will do, and launch and monitor supervised implementation with understandable recovery actions. Agents perform technical verification and independent review and bring me only the remaining sensitive judgment or authority.

The product outcome is one continuous journey: understand → prepare → select → inspect → launch once → observe → recover → see what remains. Retain the existing road overview and progressive disclosure. Give each gap an explanation, a concrete next action and a way to check closure. A proposal, prepared operation, authorized execution and observed success must have distinct text and icons as well as color.
<!-- charter: /opinion -->

## Proposed execution contract

<!-- charter: opinion -->
Keep Charter files as the road's source of truth. Store only operation identities, pinned plan inputs and execution observations in the integration. A prepared plan identifies project/repository, exact checkout and branch, base commit, selected source and document hashes, rail/unit set, dependency closure, execution order, runner capability/version, supervisor, review policy and remaining authority. Never execute arbitrary browser-supplied shell commands or derive authority from prose.

Preparation is read-only until the user requests a concrete agent task. A preparation action should create or address an actual correctly registered session with the pinned context and an inspectable delivery result, reusing platform session APIs. Existing prompt-copy fallback remains useful when dispatch is unavailable. An interview is a source of answers; its summary must still be reconciled with code and units.

At launch, the server recomputes admission against the current selected checkout and refuses changed source, stale selection, missing or cyclic dependencies, unsupported runner combinations, wrong project/user, absent supervisor, uncommitted criteria and conflicting runs. Bind submission to the inspected plan and atomically claim a persistent operation key. A double click, concurrent request, timeout retry or service restart must return the same known run, or an explicit unresolved launch state requiring reconciliation; never blindly launch again.

The current engine takes one group. Prefer a contained extension of that supported engine for an exact validated task set, or an adapter that preserves the inspected ordered plan across group boundaries. Prove the identity and dependency contract end to end. Do not implement multi-rail selection as repeated unordered Run All calls, silently rewrite tasket groups, activate the disabled meta-orchestration/Maestro families, or create a second road database. Unsupported multi-rail/chain modes have an explicit unavailable reason and a usable next step.

Show live runner identity and evidence: worktree/base/HEAD, actual worker/provider, probes and outcomes, review scope/findings/dispositions, checkpoint reason and remaining owner act. Keep failed, unknown, interrupted, human-credited and checked-pass outcomes distinct. Recovery actions call supported engine operations with fresh state/identity checks; they do not mark work done, forge receipts or clear protected gates. Technical failure returns to agents. A reserved owner act links to the existing Owner Desk item after preparation.
<!-- charter: /opinion -->

## Acceptance scenarios for the implementation rail

<!-- charter: opinion -->
| ID | Given / action | Required observation and proof |
|---|---|---|
| A1 — discover | A rail has no units, an incomplete spec, malformed records or an unsupported source. Open and select it. | Explain what is missing or unknown; offer the relevant preparation action. An empty rail never reads ready. Backend fixtures plus desktop/mobile browser traversal. |
| A2 — clarify | Sources disagree or a binding choice is unresolved. Prepare a task or interview. | Task contains exact source/revision, question actor, recommended default, expected artifact and closure check. Agent answers technical questions; genuine sensitive choices become prepared owner asks. Show actual session registration/delivery or an honest copy fallback. |
| A3 — strengthen | Units exist but probes are absent/irrelevant or spec review is incomplete. | Agent prepares meaningful base-failing probes (or explicit guards), failure modes and dependencies; independent reviewer examines spec AND units, with findings addressed and scoped re-review. Form-only checks remain labelled. |
| A4 — select | Select multiple rails with shared units, explicit cross-group edges, omitted dependencies, terminal prerequisites or a cycle. | Exact deduplicated unit set and order are visible. Unresolved dependencies/cycles block admission; satisfied prerequisites have evidence. Frontend selection and backend contract tests agree. |
| A5 — inspect | Prepare an otherwise eligible selection. | Show plan identity/base, target branch/worktree, supervisor and runner, skips/checkpoints, review mode and limits. Unsupported installed capability stays unavailable. Opening the inspection performs no launch. |
| A6 — launch once | Launch, double click, retry after response loss, race another request, or move HEAD/source after preparation. | One run at most for one accepted operation. Stale/mismatched inputs refuse before dispatch. Submitted plan equals executed task set/base, including across group boundaries. Prove concurrency/restart behavior in backend integration tests. |
| A7 — observe | Real workers implement a small disposable rail. | Every credited step has a committed change and relevant probe evidence at the judged revision; independent Anthropic review covers OpenAI-authored implementation. The page links to actual run/evidence, without converting prose into a pass. |
| A8 — fail and recover | A probe fails, runner disappears, run is interrupted, or checker result arrives after stop/HEAD movement. | Show the exact last durable state and actionable retry/reconcile/pause path. Preserve worktree and failure evidence. No duplicate workers, late false close or silent restart. Test failures deterministically and one real interruption where supported. |
| A9 — remaining human work | Encounter a protected criterion, reserved operation, private login or personal judgment. | Keep it pending and explain what remains and why. Agent performs all independent checks first. Fixtures exercise sensitive/destructive boundaries; no owner verb, receipt or acceptance is forged. |
| A10 — usable trial | Follow the whole journey on narrow and desktop viewports using keyboard. | Meaningful action labels, text/icons plus color, contextual primary actions, loading/empty/error states, source/race handling and readable recovery. Test exact intended authenticated HTTPS shell/assets/API; state whether auth/browser ran on VPS, fixture or owner device. |

Finite sequence, with each step producing inspectable commits and evidence:

1. **Contract and preparation.** Reconcile the integrated Road page with current engine APIs, installed Charter manifest and ownership. Write the assumption register, acceptance/probe plan and exact supported-runner contract. Reuse existing gap dimensions and prompts.
2. **Selection and admission.** Implement source-bound selection, dependency closure, plan preview and server-side validation. Establish tests for stale source, unsupported modes, wrong project and dependency failures before adding the launch side effect.
3. **Prepared action and launch.** Connect preparation to real session handoff; implement an atomic, restart-aware launch operation over the supported runner. Bind the run to the inspected plan; verify duplicate/race/error paths.
4. **Observation and recovery.** Connect progress, probe/review evidence, pause/interruption/retry and Owner Desk context. Preserve the distinction between checked pass, human credit, incomplete review and actual delivery.
5. **Independent review and full rail trial.** Address findings, rerun affected checks and prove A1–A10. Build a small disposable project with a finite rail, at least two dependent implementation units, meaningful existing probes and a separate review. Exercise the real available runner/supervised/chain path from planning to final evidence, with bounded runtime/resources. Add a second-rail dependency case to prove any multi-rail launch claim. Never use a client project as the test subject.
6. **Sandbox package.** Retain immutable branch/build/run/rollback instructions, trial fixtures, run IDs, revisions, logs, screenshots and review findings/dispositions. Run focused backend/frontend/integration checks, applicable repository checks and boot smoke when routing/imports change. Activate only through already authorized sandbox mechanisms; file any exact remaining owner-only action after preparing and testing it. Merge and production deployment are separate.

If the real runner or authenticated sandbox prerequisite is unavailable, finish all independent implementation and fixture tests. Record the exact command, time with timezone, result, missing prerequisite, and which scenarios remain unproved. A mock dispatch proves adapter behavior only; it cannot satisfy A7. A passing owner fixture cannot satisfy owner acceptance.

For every consequential assumption record: source/user-story basis; chosen recommendation; alternative and risk; a concrete falsification check; observed result and any correction. Re-review changed conclusions. This protocol requires evidence, not private reasoning transcripts.
